# 《交大四年：DDL战争》项目计划书

版本：v1.1｜日期：2026-10-14｜阶段：立项与原型准备

配套技术方案：[初步架构设计](初步架构设计.md)，首期开发顺序与验收唯一依据为根目录[实施计划与验收基线](../实施计划与验收基线.md)。

设计依据：[统一设计文档](交大四年_DDL战争_统一设计文档.md)。当前设定以本次四份文档融合基线为准，旧《背景设计.md》仅作不可现场复核的历史来源；本计划采用统一文档中明确标识的重设计提案。计划中的排期、成本与指标均为估算或目标，不是已有成果。

## 一、项目摘要

开发一款单人、离线、校园题材的回合制卡牌构筑游戏。玩家从交大新生开始，经历八个学期，通过作业、考试、合作和生活事件构筑牌组，完成毕业答辩，并选择升学、就业或其他去向。

核心差异是“作业战斗＋限时考试＋同学协作＋学习场景”：普通作业允许经营合作和场景，考试通过备考替代面考验牌组转换能力。题材强调校园共鸣和时间管理，不依赖现实课程知识问答。

立项目标：先证明一学期的决策循环有趣、规则可理解，再扩展四年内容。建议Windows PC首发，键鼠操作，中文优先，买断制；发行渠道和售价在试玩数据形成后确定。

当前工作区已包含四份上游 Markdown、技术契约及 G0 登记。没有 Git 仓库或 Godot 工程；旧版本“一份 MD 与 Excel、Git 删除状态”的盘点只属历史描述，无法在当前现场复核，不作为已验收代码或资产。

## 二、受众、价值与成功标准

### 2.1 目标用户

- 喜欢《杀戮尖塔》式路线选择与构筑、愿意学习有限关键词的玩家。
- 对大学生活有共鸣，希望体验轻喜剧校园叙事的学生和毕业生。
- 偏好单人、可中断、无每日签到负担的策略玩家。

### 2.2 体验目标

| 维度 | 目标 | 测量方法 |
|---|---|---|
| 上手理解 | 10名首次试玩者中至少8名能解释精力、专注、放松和DDL | 不提示复述，记录错误点 |
| 决策价值 | 大多数回合至少存在攻防、资源或目标顺序的选择 | 录像标注与访谈，不只看点击数 |
| 单学期时长 | 15～25分钟 | 排除暂停时间，统计中位数及分布 |
| 完整局时长 | 90～150分钟，允许中途保存 | 完整流程日志 |
| 完整局平衡 | 熟悉规则玩家正常难度通关率目标25%～40% | 至少每人物30个完整局，标注经验差异 |
| 规则稳定 | 阻断流程和存档损坏问题为0 | 回归测试与连续试玩 |

小样本仅用于发现问题，不能证明市场规模或平衡充分。是否继续扩内容主要依据理解成本、重复试玩意愿和实际决策质量。

## 三、范围管理

### 3.1 首个可玩切片：一学期MVP

MVP使用完整规则框架的子集，不另写一套临时玩法。未开放内容从奖池过滤，避免抽到未实现效果。

| 类别 | MVP范围 | 精确内容 |
|---|---:|---|
| 人物 | 2 | P01林序、P04唐以宁 |
| 正式牌 | 24及升级 | K01～K08、K10、K12～K16、K19、K43～K46、K51～K53、K59～K60 |
| 特殊牌 | 1 | X01分心消息 |
| 单位 | 4 | F01～F04 |
| 场景 | 3 | L01～L03 |
| 饰品 | 8 | A01、A04、A05、A07、A08、A11、A15、A18 |
| 普通任务 | 4 | N01～N04 |
| 精英 | 1 | Q01 |
| 首领 | 1，3阶段 | B01高数期末 |
| 事件 | 4 | V01、V03、V04、V10；V03用MVP可用的K14/K05/K60作为版本化生产 MVP 覆盖池（完整版本池不变） |
| 地图 | 1学期，6层、8图节点对象，每条路线经过6节点 | 普通→分支→商店→普通/精英→休息→首领 |
| 配套 | 完整闭环 | 教学、奖励、商店、休息、设置、保存/继续、失败重开、战斗日志 |

MVP只开放正常DDL难度，关闭履历、传承、完整结局；结束显示“第一学期完成”。商店/奖励品质缺项时执行统一文档的合法池重归一化规则。生产 manifest 目标名为 campus_mvp；V03 显式覆盖池 K14/K05/K60，N04 显式覆盖可出现学期为 [1]（完整定义为第2～3学期）。两项 override 均携带范围版本及来源；完整版本保留原定义，测试 fixture 独立。B01 最后阶段胜利直接完成切片，不发终点后的生活费/奖励，不进行下一学期恢复、履历或毕业去向选择；保留终局摘要。该终点约定落实“第一学期完成”的范围，不借用 B08 毕业逻辑。

### 3.2 完整v1.0

4人物、60正式牌及升级、3特殊牌、8单位、6场景、24饰品、12普通任务、4精英、8首领（14个阶段实例）、12事件、8学期共48个经过节点、64个图节点对象、3难度、6种毕业去向与失败总结。

另需主菜单、图鉴、设置、教学、存档、战斗日志、完整奖励/商店/休息、履历和基础传承解锁。卡牌升级共60套效果差异，不要求另画60张卡图。B05三条路线共用机制，仅更换叙事表现。

### 3.3 后续版本储备

每日挑战与排行榜、联网账号、云存档、多语言、移动端、多人合作、配音、复杂程序化地图、新专业牌池和更多结局支线。首版不为这些系统预先实现服务端。

### 3.4 变更规则

每个新需求先记录：影响的设计ID、玩家价值、开发和测试成本、替换哪项现有工作、是否改变关键路径。锁版后新增内容进入后续版本；必要的规则修复同步更新设计文档、数据和验收用例。

## 四、技术方案与制作流程

### 4.1 技术建议

建议Godot 4稳定版与GDScript，适合2D界面和轻量单机发行。第一周确认具体版本并锁定。此处是实施建议，不代表已验证历史项目可复用。

- 战斗核心采用纯状态与命令处理，尽量不依赖场景树；界面消费事件日志展示动画。
- 游戏内容以JSON定义，永久实例ID与定义ID分离。MD记录设计意图，JSON作为实际运行数值唯一来源。
- 固定种子随机，map/reward/event/battle 四条随机流分开；存档记录种子与随机进度。
- 优先实现直接对应现有牌效的处理器，不先做可视化脚本编辑器或通用规则语言。
- 自动校验ID唯一、引用存在、费用与数值范围、效果类型合法、池中有可抽对象。

### 4.2 模块与交付边界

| 模块 | 职责 | 交付物 |
|---|---|---|
| 内容数据 | 人物、牌、单位、场景、饰品、遭遇、事件 | JSON定义、校验器、设计ID映射 |
| 战斗核心 | 出牌校验、回合、触发、结算、胜负与阶段 | 可无界面运行的战斗模拟和规则测试 |
| 局流程 | 地图、奖励、商店、休息、履历和结局 | 完整Run状态、节点推进、交易原子性 |
| 展示交互 | 卡牌、意图、单位、场景、提示和选目标 | 键鼠可用界面、减少动画、字体设置 |
| 存档 | 当前局与永久解锁分离，版本号与备份 | 原子保存、恢复、旧版本处理策略 |
| 质量工具 | 种子复现、日志导出、数据检查 | 自动测试入口、问题复现包 |

### 4.3 存档基线

autosave 开启时至少支持节点完成、战斗内稳定行动边界自动保存，以及菜单显式保存退出；关闭时只显式写盘。稳定边界指规则结算队列完成，与动画播放进度无关，不保存半条效果队列。保存内容包括牌实例、各牌堆、阶段、DDL、触发次数、单位、场景与随机进度。

先写临时存档、校验成功再替换正式档，保留上一份可恢复备份。同版本退出重进不能刷新商店、奖励或宿舍随机结果。跨数据版本不承诺战斗中无损迁移，但必须清晰提示并保护永久解锁。

### 4.4 资产工作量建议

完整版本规划4套主角立绘及头像、8个合作单位形象、任务主体共24种视觉定义（12普通+4精英+8首领）、6个战斗场景、24个饰品图标、60张卡面图、12张事件主图与一套结局模板。首领阶段优先以叠层和动作区别，不强制逐阶段另画立绘。

地图背景、卡牌边框和状态图标采用可复用组件；卡面可以共用人物局部和道具素材，但必须能区分牌义。G0–G5 只在根目录 动作或者图片描述/ 登记文字需求；G6 按台账生成并核对图片，G7 才补齐具体布局/动作设计并实施 UI。不得提前制作占位布局或界面。

## 五、人员与职责假设

基线团队为4人全职，加阶段性外包：

| 角色 | 主要责任 | 验收责任 |
|---|---|---|
| 制作人/策划 | 范围、排期、规则、数值、事件文案 | 规则与体验、内容一致性 |
| 玩法程序 | 战斗、触发、数据、自动测试 | 结算正确、可复现 |
| 客户端程序 | 界面、局流程、输入、存档和构建 | 完整闭环与稳定性 |
| 美术/UI | 视觉规范、角色、卡图、图标、界面 | 可读性、资产一致性 |
| 外包音频/测试 | 音效音乐、独立试玩与兼容性 | 素材清单与问题报告 |

以上仅为团队角色模型，按用户要求不维护每日负责人，只记录决策和验收日期。策划维护唯一内容表，程序不在界面脚本中藏平衡数值。

若实际只有一名开发者，应将第一阶段目标固定为MVP，建议先按12～18周估算切片，再依据实测速率重估完整版本；不能直接沿用四人团队的完整版本日期。

## 六、里程碑与排期

基线为四人团队24周，W1从实际立项日算起。验收未过先修复或缩范围，不因日期到达自动进入下一阶段。

| 阶段 | 周期 | 核心任务 | 交付与退出条件 |
|---|---|---|---|
| M0 立项与盘点（G0–G2） | W1～W2 | 来源/范围/规则冻结、工程骨架、内容和基础状态；UI 文字需求 | G0 核查、G1 工程命令、G2 schema/ID/RNG 校验；不含出牌原型或界面 |
| M1 战斗原型（G3） | W3～W5 | 回合、专注、抽弃牌、意图、单位、场景、考试、阶段 | MVP涉及的牌效可运行；核心边界测试通过；固定种子可复现 |
| M2 可玩切片（G4–G8） | W6～W9 | 24牌等MVP内容、六节点闭环、交易、存档、基础教学 | 两人物都能完成一学期；至少10人新手测试；无阻断流程问题 |
| M3 内容扩展 | W10～W15 | 其余人物与牌池、八学期、敌人、事件、履历、结局 | 完整路线48节点可走通（地图共64个节点对象）；全部数据ID校验通过；内容冻结 |
| M4 Alpha与调优 | W16～W19 | 完整美术接入、音效、三难度、传承、数值迭代 | 每人物30个完整局；完成量、费用、考试转化等重点复核 |
| M5 Beta与发行准备 | W20～W22 | 兼容性、存档回归、可读性、商店页面与试玩包 | 严重缺陷清零、目标硬件通过、可安装候选包 |
| M6 缓冲与发布 | W23～W24 | 回归、打包、修复发行阻断问题 | 最终清单通过、发布候选版本封存、已知问题说明 |

### 6.1 关键路径

G0 基线 → G1 骨架 → G2 内容/状态 → G3 战斗 → G4 局流程 → G5 存档及无头闭环 → G6 图片 → G7 UI → G8 MVP 验收；此后再启动 M3–M6 完整版本内容、平衡与发布。

可以并行准备文档、数据候选与测试输入，但不能越过阶段出口：G0–G5 美术和客户端只登记图片/动作文字需求；G6 生成核对图片，G7 才做详细视觉、节点/菜单和战斗 UI。四人24周只是估算，尚无实际立项日；单人12～18周 MVP 也需按实测速率重估。

## 七、预算估算

以下是人民币成本模型，不是报价。假设24周约6个月、4人全职；人月综合成本含薪酬及基础用工负担。场地、税费、渠道服务费的实际口径需立项时确认。

| 项目 | 假设 | 估算 |
|---|---|---:|
| 核心人力 | 24人月×1.5万～2.5万元 | 36万～60万元 |
| 美术补充外包 | 卡图、事件图等峰值需求 | 3万～8万元 |
| 音频 | 音乐与音效制作/授权 | 1万～3万元 |
| 独立测试与设备 | 试玩组织、兼容设备或服务 | 1万～2万元 |
| 工具与发行物料 | 素材工具、宣传图、视频等 | 1万～3万元 |
| 小计 | 以上合计 | 42万～76万元 |
| 预备金 | 小计15% | 6.3万～11.4万元 |
| **总计** | **基线团队完整版本** | **48.3万～87.4万元** |

不计入未确定的付费买量、长期运营、服务器和跨平台移植。若自研不发工资，可降低现金支出，但人力机会成本仍应记录。M2结束后应按真实人周、资产单价和返工量重估，而不是把预算区间当固定承诺。

商业测算只采用公式：回本销量≈总投入÷每份净收入。每份净收入应扣除渠道、税费、退款和折扣；目前未确定售价和销量数据，不编造收入预测。

## 八、质量与验收

### 8.1 自动检查

1. 数据：定义ID唯一；所有引用存在；MVP配置无越界内容；候选池不足有确定回退；升级效果不缺字段。
2. 战斗：统一文档T01～T20；另覆盖群体完成、触发先后、保留、耗尽恢复、同名能力、护卫逐段改向。
3. 流程：交易取消无变更；删牌下限；奖励只领一次；节点不能回退；失败不能继续领奖。
4. 存档：中途退出恢复全部状态；次数与随机序列一致；写入失败能用备份恢复。
5. 构建：干净环境能导出并启动发布包；正式包不开放调试加钱或跳关入口。

### 8.2 人工体验与兼容性

- M2至少10位首次接触者；分别记录不理解的词、误操作、死亡原因及愿不愿再试一局。
- M4至少120个完整局（4人物×30），由多个测试者完成，保存种子、版本和死因。先按每局90分钟估算约180小时纯游玩，另预留记录和复核时间。
- 目标硬件初案：Windows 10/11、8GB内存、集成显卡、1920×1080；同时检查1280×720及高DPI字体。正式最低配置由实测确定。
- 性能目标：G7/G8 在参考机验证普通战斗60FPS；规则命令 P95≤50ms 且单次≤100ms，冷启动内容加载≤2s，≤1MiB快照保存 P95≤1s；动画可加速或关闭，复杂结算不能阻断输入状态恢复。
- 存档损坏、无法结束回合、无法退出目标选择、奖励重复领取、考试规则绕过属于发行阻断项。

### 8.3 完成定义

功能只有在数据、实现、交互、日志、必要测试和文档一致时才算完成。“能看见界面”或“策划表写完”不等于功能验收。内容牌至少验证普通/升级、合法/非法目标及与核心状态交互。

## 九、风险与处理

| 风险 | 预警信号 | 处理措施 | 责任人 |
|---|---|---|---|
| 八学期过长 | 完整局普遍超过150分钟或中途退出率高 | 先压缩动画、普通战回合和重复事件；保留八学期语义 | 策划 |
| 合作流考试失效 | P04在首领出现明显断崖胜率 | 调备考面及通用输出获取；检查考试预告是否足够 | 策划/玩法程序 |
| 回费抽牌循环 | 单回合资源净增长且可重复 | 用耗尽、实例限次修正具体牌；增加循环复现测试 | 玩法程序 |
| 场景/饰品叠加过强 | 自习室＋耳机形成无代价优势 | 分析牌效预算、奖励频率及触发上限，不直接全局削弱 | 策划 |
| 美术产量不足 | W12后资产完成不足计划的一半 | 优先统一轮廓与图标，共用背景叠层，减少非必要动画 | 美术/制作人 |
| 存档复杂 | 读档重置次数或随机结果 | 在M2前实现完整状态序列化与对照回放 | 客户端程序 |
| 历史代码复用误判 | 旧规则大量依赖融牌与快照场景 | W2前做复用评估，必要时只复用界面组件 | 程序负责人 |
| 数值样本偏差 | 单人测试占绝大多数 | 多测试者、固定种子组和自由局结合 | 制作人 |
| 范围持续增长 | 新牌和新系统超过冻结清单 | 以替换旧任务方式排入，否则移到后续版本 | 制作人 |

## 十、发布与维护

1. M2内部试玩验证规则，M4根据稳定性决定是否开放外部试玩；对外试玩只承诺当前可玩范围。
2. M5准备产品介绍、截图、玩法短片、系统配置和反馈渠道。宣传主打校园学习决策，不把所有储备玩法写成已有功能。
3. 发布前冻结内容与存档版本，执行安装、首次启动、全流程、退出恢复和卸载后用户数据保留检查。
4. 发布后前两周优先处理阻断与存档问题，之后根据拿牌率、完成时长和体验反馈排平衡补丁。
5. 每次平衡更新注明受影响ID与存档处理；玩家可导出本地日志用于反馈，首版不依赖在线遥测。

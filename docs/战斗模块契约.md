# 战斗模块契约（src/battle/**）

> 来源：《接口文档》§4、《初步架构设计》§10.3，以及[游戏规则书](交大四年_DDL战争_游戏规则书.md)的固定规则编号。
> 本文件是该模块对外的唯一契约说明；字段含义与取值范围以此为准。
> 本文件描述目标行为，不证明实现或测试已存在。规则与范围已在 G0 文档融合；实现与数值接入须在所属阶段验证；测试路径为建议命名。

## 1. 入口

```gdscript
var engine := BattleEngine.new(content_db)   # 只读内容库，可空后再 set_catalog()
engine.begin(input) -> Result<BattleStep>
engine.preview(state, draft) -> Result<ActionPreview>
engine.apply(state, action, rng_state) -> Result<BattleStep>
engine.make_view(state) -> BattleView
engine.resolve_face(state, card_id) -> Result<EffectiveCard>
engine.calculate_cost(state, card_id) -> Result<CostQuote>
```

- `preview` / `calculate_cost` / `make_view` 不改变状态、不消费随机。
- `preview` 返回的 `ActionPreview.revision` 在 BattleEngine 层固定为 `-1`（未绑定）；只有 GameSession 从唯一会话状态写入实际 revision，BattleState 不持有 revision。
- `apply` 在 `state.copy_for_write()` 的工作副本上结算：失败返回 `Result.fail`，调用方状态不变。
- `begin` 与 `apply` 的 `rng_state` 必须传 `RandomSource.export_state()` 的完整四流快照；本模块只推进 battle 流，其余流原样返回。生产接口不得以零种子静默补缺。测试也应显式提供固定种子，保证用例可复现。

### 1.1 G3-02 入场切片

G3-02 的 `begin` 实现会校验输入字段、引用和完整 RNG 快照，构造战斗卡牌/首阶段任务，注册人物与任务来源，使用 battle 流洗牌，再执行首次准备并返回 `player_action` 稳定状态。首轮准备运行已接线的 `round_start` hook、基础抽牌及 `draw` hook；抽牌受 `draw_per_round`、`hand_limit` 和剩余牌数共同限制。初始任务取 Encounter 的首个成员及其首阶段/首个意图；DDL 为 `max(minimum_ddl, base_ddl + difficulty.ddl_offset)`。

遭遇 scaling 以及 schema 中尚无执行映射的 hook 类型仍返回 `ENGINE_NOT_READY`，不发布部分状态。输入引用缺失/未启用仍返回带 `kind/id/path` 的 `CONTENT_INVALID`。抽牌与 shuffle 只推进 battle 流；其他三流和传入快照不变。无随机效果的首轮 hook 不会在洗牌之外推进 RNG。

2026-10-16 入场边界修订：`shop_price` 已由局流程的 `RewardGenerator.price_for` 实现，属于合法的非战斗 hook；携带该类饰品（生产 A15 校园卡）必须可进入普通、精英和首领战。BattleEngine 保留饰品及其来源登记，但不触发商店折扣、不消费对应计数或随机流；战斗效果按各自触发点运行。不能通过删除饰品或静默放行未知 hook 规避错误。覆盖证据见 G7 执行记录的校园卡入战修复。

### 1.2 G3-03 动作预览与预检

G3-03 实现 `BattleEngine.preview(state, draft)`、`resolve_face` 和 `calculate_cost`。动作草稿当前只执行 `play_card` 预检；已知但尚未实现预览的战斗动作返回 `ENGINE_NOT_READY`，未知动作类型或 payload 白名单之外的键返回 `INVALID_ARGUMENT`。无效实例、阶段、目标、费用、限次和不可打出卡面以成功的 `ActionPreview` 返回，由 `blocking_errors` 阻止提交；请求格式错误和内容/内部错误才返回失败 `GameResult`。

`resolve_face` 先应用升级 patch，再依据 `exam_flags` 解析独立作答/固定考场替代面。`calculate_cost` 与 `preview` 共用该有效卡面，返回 `CostQuote = {base, added, discount, cost, sources, vitality_base, vitality_discount, vitality_cost}`；本切片尚不加载饰品，未实现的折扣源保持 `added=0`、折扣为0、`sources=[]`。`preview.costs = {focus, vitality, quote}`，其中 `focus` 与 `vitality` 是实际报价整数。主动精力预检按 `vitality - vitality_cost >= minimum_vitality_after_payment` 检查。

战斗卡实例 `temporary_modifiers` 当前必须为空字典；非空或非字典值在 `resolve_face` 阶段返回 `ENGINE_NOT_READY`。临时费用修正尚无 G0 冻结的字段/来源映射，本步骤不得忽略或自定义其解释；待对应效果接线时扩充此契约及用例。

目标为 `task` 或直接作用于 `unit` 且草稿尚未选择时，`required_selections` 加入 `{field, kind, candidates, min_count, max_count}`，同时以 `INVALID_TARGET` 列入 `blocking_errors`；每个候选为 `{id, label_key, preview}`。任务候选只包含 `eligible_round <= round_index` 且仍有工作量的任务。`summon_unit` 在单位槽未满时不要求替换；槽满时从活单位生成 `field=replace_unit_id`、`kind=unit_replacement` 的候选并要求选择，`target_ids` 不代替该字段；公共 payload 中 `replace_unit_id: null` 等价于未提供。自我或全任务目标不要求选择。`known_effects` 保持有效卡面的 `pre_effects` 后接 `effects` 顺序；预览不执行效果队列、不扣资源、不移牌、不增计数、不消费随机。限次读取 `BattleState.counter_key(per, origin_card_id, "play_card")`；无永久来源时使用战斗卡实例 ID。

### 1.3 G3-04 结算与轮末执行

`apply` 在副本上完成整条效果队列；效果中产生的 `pending_choice` 会把 `phase` 置为 `awaiting_choice`，只接受匹配的 `confirm_choice`，确认后继续同一队列。选择失败不改变输入状态或 RNG。完成量在每个队列段开始时重新检查目标；阶段归零先创建新的任务实例，锁定旧任务的后续段直接跳过。终局检查在每个不可拆分效果及合作行动后执行，最后任务完成立即停止后续续航、压力与 DDL。

`end_turn` 的执行顺序固定为：`player_action_end` 到期 → `ally_action`（开始时快照单位，按 `entered_order` 行动）→ `discard` → `enemy_prepare` 清屏障 → `enemy_skill` 处理屏障/恢复/状态/加牌 → `enemy_pressure` 逐段重新选择护卫或主角 → `round_end` 场景效果与状态到期 → DDL 检查 → 意图轮换和下一轮准备/抽牌。合作行动消耗单位精力并在归零时立即暂离；护卫只改向默认单体压力，伤害不溢出。场景准备随机结果在建立和每次结算后预抽并保存，建立当轮不触发。

单位 `guard=true` 只创建一份 `guard` 状态；护卫选择按最小 `entered_order`，单位离场同时移除其状态。意图的 `eligible_round` 大于当前轮时跳过该轮敌方行动。未注册效果或不支持的选择上下文继续返回 `ENGINE_NOT_READY`，不得静默忽略。

## 2. BattleInput（begin 入参，Dictionary）

| 字段 | 类型 | 说明 |
|---|---|---|
| battle_id | String | 调用方生成的非空、局内唯一战斗实例 ID，也是战斗内自造 ID 的前缀 |
| node_id | String | 地图节点，可空 |
| encounter_id | String | 遭遇定义 ID（必填，必须在清单内启用） |
| character_id | String | 人物定义 ID，用于 P01 被动等 |
| difficulty | String | relaxed / normal / hard；取 `difficulty_overrides` |
| vitality | int | 入场当前精力，缺省为 max_vitality |
| max_vitality | int | 入场最大精力，缺省为 `run.starting_vitality` |
| cards | Array | 永久牌实例快照：`{card_id, definition_id, upgrade_level}`；引擎新建战斗 card_id，并用 origin_card_id 关联输入永久 card_id；全部进抽牌堆后洗牌 |
| relics | Array | 调用方按 slot 升序给出的饰品定义 ID 数组（如 `["A01"]`），引擎保持数组顺序 |
| rng_state | Dictionary | 必填的完整四流快照（`RandomSource.export_state()`）；缺失返回 `INVALID_ARGUMENT`，不创建战斗 |

`begin` 的输入 Dictionary 只接受上述字段；`battle_id`、`encounter_id`、`character_id` 和永久 `card_id` 必须是唯一/有效的 ASCII 标识符，卡牌实例对象只接受表中三个字段。G3-02 暂不接受带 `scaling` 的遭遇或非空 `relics`，返回 `ENGINE_NOT_READY`。

### 2.1 输入引用校验

`BattleEngine.begin()` 必须校验 encounter、cards、relics 及其传递引用都存在于本局已加载的内容集。引用缺失或未启用时返回可定位的 `CONTENT_INVALID`，不得静默忽略效果。RunService 已按 slot 升序提供定义 ID 数组；BattleEngine 保持此顺序注册来源，不对字符串读取不存在的 slot 字段。相同状态和输入顺序必须得到相同结算结果。

## 3. BattleStep（begin/apply 返回）

| 字段 | 类型 | 说明 |
|---|---|---|
| state | BattleState | 工作副本，成功时才是可发布的新状态 |
| events | Array<RuleEvent> | 本次增量事件；见 §6 |
| pending_choice | ChoiceRequest 或 null | 效果内选择；非空时必须先 confirm_choice |
| outcome | BattleOutcome 或 null | 非空表示战斗已结束 |
| stable | bool | 规则队列为空且没有待处理选择；终局 `outcome` 可以非空且仍为稳定状态 |
| rng_state | Dictionary | 本次执行后的完整四流快照；仅 battle 流可变化，与状态共同提交或共同回滚 |

BattleOutcome：`{battle_id, result, reason, remaining_vitality, summary}`；
`result ∈ won/lost/abandoned`，`reason ∈ tasks_completed/vitality_depleted/deadline_expired/abandoned_by_player`。

## 4. 相位机

显式顺序（`BattleEngine.PHASE_ORDER`），不依赖字典遍历：

```text
player_prepare -> draw -> player_action -> ally_action -> discard
  -> enemy_prepare -> enemy_skill -> enemy_pressure -> round_end
  -> （round_index+1、推进意图）player_prepare ...
```

- `begin` 自动推进到第一个 `player_action`（或待选/终局）。
- `end_turn` 从 `player_action` 连续推进到下一轮 `player_action`。
- `apply(play_card)` 只结算该牌，不自动结束回合。
- `awaiting_choice` 是待选暂停态；`finished` 后由 `outcome` 说明结果。

## 5. 结算约定（来源固定规则，运行待验证）

- 完成量：`max(0, floor((基础 + 适用固定加值 - 惩罚) × 适用倍率))`，先扣任务屏障，再减未完成量，不结转超额。
- 压力：先扣放松，再减精力；主动支付精力绕过放松。
- 费用：`max(0, 基础费用 + 加费 - 减费)`；一次性优惠在对应合法出牌成功后消费。
- DDL：还能经历的轮末次数；先完成救命替代与强制阶段，再检查主角精力归零（优先失败），再检查最后任务完成；胜利后停止队列、续航扣费及 DDL；扣到 0 仍有任务则 `deadline_expired`。
- 阶段转换：旧阶段归零先生成新 `task_id`，旧目标多段跳过，不提前判胜。
- 随机：只有 `RandomSource` battle 流被本模块推进；preview 与失败操作不消费随机。

## 6. RuleEvent（events 元素）

每个事件沿用[接口文档 §8](接口文档.md)的统一结构：`{index, type, source_id, target_ids, data}`。`index` 是本次结果内从 0 递增的序号；`source_id` 可空，`target_ids` 为空时用 `[]`，效果载荷全部放在 `data` 中，不平铺到事件顶层。下列是目标事件类型，须在 G1 类型定义和相关阶段用例中落实：

`phase_changed`、`round_started`、`focus_changed`、`card_played`、`card_resolved`、
`card_drawn`、`card_discarded`、`choice_requested`、`choice_confirmed`、`status_gained`、
`status_removed`、`completion_applied`、`pressure_applied`、`vitality_changed`、
`unit_summoned`、`unit_departed`、`scene_established`、`scene_replaced`、
`task_advanced`、`task_completed`、`work_restored`、`enemy_skill`、`ddl_ticked`、`battle_finished`、
`coop_target_set`。

事件类型及 data 的唯一表见接口 §8；稳定字符串由 GameConstants 提供；UI 只读，不得据此修改规则状态。

## 7. Action 与 ChoiceRequest

Battle 动作沿用 `GameAction = {type, payload}`：

| type | payload |
|---|---|
| play_card | card_instance_id、target_ids、replace_unit_id（可空） |
| confirm_choice | choice_id、selected_ids |
| set_ally_target | unit_instance_id、task_instance_id |
| end_turn | retained_card_ids |

ChoiceRequest：`{choice_id, kind, prompt_key, candidates:[{id,label_key,preview}], min_count, max_count, source_card_id, effect_amount}`。

命令字段名与公共接口一致；`card_instance_id` / `unit_instance_id` / `task_instance_id` 的值分别引用视图中的 `card_id` / `unit_id` / `task_id`。视图和实体的短字段名不构成另一套命令格式，不接受两套隐式别名。

## 8. BattleView（make_view）

顶层：`battle_id/node_id/encounter_id/phase/round_index/ddl/character_id/difficulty/
relics/exam_limits/player/hand/zones/units/tasks/statuses/scene/pending_choice/outcome/
stable/phase_order/zones_public`。

- `player`：`{entity_id, vitality, max_vitality, relax, focus}`
- `hand[]`：`{card_id, definition_id, origin_card_id, upgrade_level, effective_cost, effective_vitality_cost, playable, face}`；两种有效代价由同一费用解析提供，playable 包含专注、精力、不可打出、限次与无需目标选择即可判定的门槛；需要玩家目标时由preview补全选择并最终校验，不能只看专注。
- `zones`：五区计数 `{draw, hand, discard, exhaust, resolving}`
- `tasks[]`：`{task_id, definition_id, phase_key, work_remaining, work_max, shield, entered_order, eligible_round, intent}`
- `scene`：`{scene_id, definition_id, established_round, pending_random_result}` 或 null
- `zones_public`：仅含弃牌堆与耗尽堆的卡面数组，与 `hand[]` 同构；抽牌堆和结算区只提供计数，遵循[接口文档 §2](接口文档.md)和[界面层契约 §15.7](界面层契约.md)。

## 9. 战斗内实例 ID 与触发计数

- 战斗内自造实例 ID = `<battle_id>|<prefix><n>`（prefix：p/t/u/s/c/st/ch），单调不复用、不消费随机；
  永久牌实例 ID 仍由 `RunState` 分配并作为 `BattleCard.origin_card_id`。
- 触发计数键 = `BattleState.counter_key(scope, owner_key, trigger_key)`，
  `scope ∈ round / instance_round / battle`（`GameConstants.COUNTER_SCOPE_*`）。
  回合类计数在玩家准备阶段重置；实例限次的 `owner_key` 用 `origin_card_id`，换场/回收不刷新。
- `TaskState.intent_snapshot` 为当前公开意图的 Dictionary 副本；`intent_cursor` 每轮末 +1。

BattleState.next_creation_order 与 source_registry 保存单调创建序和来源值记录；人物→按输入顺序的饰品→遭遇任务初始化注册，后创建单位/场景/状态依次分配。触发按 (creation_order,source_instance_id,effect_index) 排序；同一次稳定保存/恢复必须保留计数和历史来源，不能按现存对象重新编号。详见规则书[RES-001]。

BattleState 还持有 `character_id`、`difficulty`、`exam_flags` 与 `next_instance_seq`。人物 `player.entity_id` 使用 `p` 前缀；遭遇任务使用 `t` 前缀；战斗卡牌使用 `c` 前缀并保存 `origin_card_id`。`next_instance_seq` 只生成实例 ID，`next_creation_order` 只排序触发来源。

## 10. 效果内选择（步骤 2）

- K03「抽2弃1」：`draw` 先执行，随后 `discard` 产生 `pending_choice`；
  候选 = 抽牌之后的手牌（含新抽到的牌），`min_count = max_count = 1`。
- 待选期间 `state.resolution != null` 且 `phase = awaiting_choice`：
  `play_card` 与 `end_turn` 一律返回 `CHOICE_PENDING`；`confirm_choice` 数量/候选非法时
  返回 `INVALID_ARGUMENT` / `INVALID_TARGET` 且**不清除原待选**。
- 未提交 = 未支付：`preview` 与任何被拒绝的 `apply` 都不扣专注、不移牌、不消费随机。
  一旦支付并进入待选，候选契约要求不能取消整张牌；依据规则书 [PLY-002]；支付前预选可免费取消，支付或信息揭露后的强制待选必须完成。
- `ResolutionState.choice` 是待选真相（跨调用保留在 state 里）；`BattleStep.pending_choice`
  是同一份数据快照。

## 12. 状态到期时点（目标规则，逐项对照上游规则书）

| 状态 | 数值效果 | 清除时点（`StatusState.expiry`） |
|---|---|---|
| 灵感 | 工作牌第一段每层 +2（上限5） | 打出工作牌时 / 未用轮末（`round_end`） |
| 编译/实验数据/引用/复习 | 牌面显式读取或消耗 | 本战（不自动清除） |
| 心流 | 工作第一段每层+1；有层数时回合回能+1 | 本战 |
| 焦虑 | 下次准备每层少回 1 专注 | 生效后（`prepare`） |
| 拖延 | 下次基础抽牌每层少抽 1 | 生效后（`draw`） |
| 困倦 | 玩家工作牌第一段每层 -1 | 下一 player_action 结束、ally_action 之前；该行动内每张工作牌第一段均受影响，上限2 |
| 护卫 | 不叠加的存在标记，改向默认单体压力 | 单位离场 |
| 额外要求 | 任务每层压力 +2 | 本战 |
| 查重护盾 | 任务屏障值 | 敌方准备清零（`enemy_prepare`） |

## 13. 单位（步骤 3）

数据：`data/definitions/units.json`，字段 `id / name_key / vitality / cooperation / guard / support / entry_effects`。

- 召入：`summon_unit` → 检查 `battle.unit_slots`；满槽时必须提供 `replace_unit_id`，否则 `INVALID_TARGET`
  （取消 = 不提交，不扣费、不移牌）。
- 换班：旧单位移出（原因 `switch`）→ 新单位进入并分配新 `entered_order`；不触发暂离奖励。
- 暂离：精力归零立即移出（原因 `exhausted`），其状态一并移除。
- 合作阶段开始先快照当前存活单位 ID，按 `entered_order` 升序，每个单位每回合最多一次；期间新召入单位不在快照中、本次不行动——
  支援（`support`）→ 协作完成（`cooperation`）→ 自身失去 `battle.unit_action_vitality_cost` 精力（绕过放松）。
  协作目标优先 `UnitState.target_id`，失效回退行动顺序最前任务；完成最后任务立即胜利并停止后续步骤。
- `support.kind`：`relax / self_relax / cleanse_or_relax / gain_status_on_actions / heal`。
- `UnitDef.guard=true` 只用于入场创建一份 guard StatusState；运行时以该状态是否存在为唯一依据，不在 UnitState 维护第二个 guard 真相。

## 14. 护卫与压力改向

- 默认单体压力目标 = 最早入场的存活护卫（`entered_order` 最小），否则主角。
- 每段压力重新选目标；伤害不溢出：目标精力归零立即暂离，剩余伤害不转给主角。
- 全体压力（`pressure_all`）与显式点名不经过护卫改向。

## 17. 多阶段任务与转阶段

- `TaskState` 由 `(definition_id, phase_key)` 定位，`phases` 顺序推进。
- 阶段归零：**先**生成下一阶段的新 `task_id`（清旧屏障与状态，旧 task_id 不再存在），**再**由调用方在完整连锁结束后判定胜负，不提前胜利。
- 旧目标多段：`ResolutionState.locked_target_ids` 指向旧 task_id 时，后续段**直接跳过**（不结算、不改任何 task）。
  这条由 `_primary_task` 的两个分支保证，别把它们合并：
  - **给了锁定目标、但目标已不存在或已归零** → 返回 `null`，本段完成量丢弃（若回退到新阶段，等于替玩家白打一个阶段，且悄无声息）；
  - **本来就没给目标**（场景 / 单位 / 饰品效果传空数组）→ 才回退到首个合法任务。
  即使首期内容暂时没有跨阶段多段效果，也必须用合成两段队列覆盖该边界：建议测试名 `test_phase_segments.gd`。
- `eligible_round`：玩家侧阶段生成的任务当轮可行动；敌方行动中生成的新任务 `eligible_round = round_index + 1`。
- 新阶段不承接旧阶段超额完成量（`work_remaining` 由新阶段 `work_max` 重置）。

### 19.1 效果内选择（一次只允许一个待选）

- 四个 kind 共用同一套机制：`ResolutionState.choice` 是唯一真相，`BattleStep.pending_choice` 是它的快照；
  `kind ∈ discard / recall / purify / retain`（`GameConstants.CHOICE_*`），候选统一为 `{id, label_key, preview}`。
- `_execute_queue` 遇到需要选择的 op 就调 `_start_effect_choice` 并**立刻返回**（`phase = awaiting_choice`）；
  `_confirm_choice` 校验数量/候选后追加 `choice_counts[kind] = 实际生效数量`、游标 +1，再继续队列。
  因此同一时刻只可能有一个待选：待选期间 `play_card` / `end_turn` 都是 `CHOICE_PENDING`，
  K03 的「抽后弃」与 K07/K12 的新选择天然串行，不会互相插队。
- 待选请求新增字段 `effect_amount`（该效果的 `amount`，如净化层数）；`preview` 里带各自的上下文
  （角色/状态 id + 层数）。
- 需要选择的 op 只能写在卡牌效果里（内容校验强制）：场景/饰品/被动/单位支援没有挂起再回来的上下文。

### 19.2 其它引擎增量

- `pre_effects` 的目标语义为**整张牌结算前执行一次**，基础定义与 `upgrade` 都支持；考试替代面清空 `pre_effects`。实现与用例必须验证此时序。
- `retain_hand_card` 的目标语义为：执行时选择并标记另一张手牌；被标记牌离手立即失效，轮末仍有效则跳过弃牌并清除标记。未消费的标记是稳定战斗状态的一部分，必须随 BattleCodec 保存；end_turn.retained_card_ids 只用于其他来源明确授予的普通保留额度，默认0。
- 目标事件类型包括 `card_recalled` / `retention_granted`；载荷已在接口§8冻结，实现后以用例验证。
- X01 与 N03 已进入冻结MVP目标；只有定义、引用闭包和测试 fixture 均通过，才可接受该组合。
- 特殊牌rarity=null，普通随机奖励排除basic/special标签，候选池行为在G2验证。


## 20. 严格校验：不允许静默失败

核心规则：**引擎不会做的事，不许被静默忽略或近似掉**。JSON 写法见[内容层契约 §7.6](内容层契约.md)、§7。

### 20.1 主动支付精力

- `BattleCardRules.resolve_face` 把 `vitality_cost` 带进卡面（基础 + `upgrade` 覆盖，都是 int）。
- `cost_quote` 返回 `vitality_base / vitality_discount / vitality_cost`；`vitality_cost` 不再硬编码 0，
  减免源接在统一的 `vitality_discount` 上；K10/A08及设计值已登记于G0；G2/G3验证内容和支付接线。
- `validate_play`：`精力 - vitality_cost >= battle.minimum_vitality_after_payment`（配置键不再悬空），
  不足返回 `INSUFFICIENT_RESOURCE` / `error.play.not_enough_vitality`，且在任何写入之前返回
  （不扣费、不移牌、不推进随机、不加计数）。
- `_play_card`：与专注费同一步支付，直接扣 `player.vitality` 并发 `vitality_changed{paid}`；
  绕过放松（与压力伤害不同）。`make_view.hand[].effective_vitality_cost` 与 `preview.costs.vitality` 同源。
- 内容侧撤回 K10 的近似：`{"op": "lose_vitality", "amount": 4}` → `"vitality_cost": 4`（升级 3），
  `effects` 只剩 `gain_focus 2`。`lose_vitality` 保留给非压力精力损失（L06 轮末）；事件主动支付只用 cost.vitality，必须留1。

### 20.2 未注册状态在加载期被拒

- 设计目标包括 `GameConstants.WIRED_STATUS_IDS`（允许写入的状态清单）与
  可定位缺失语义的内容校验错误；具体常量形式由 G1 类型/命名约定冻结。
- `ContentDB._check_status_wiring` 挂在 `_validate_effect_list`（卡牌/饰品/场景/单位/被动/upgrade
  全覆盖）与 intent 的 `gain_status` 上：未接线或未定义一律 `CONTENT_INVALID`，消息写出缺口。
- 每个未注册或尚无完整结算语义的状态都必须被拒绝；实际缺口由内容缺口账本逐项列出，不在本文件声称某个状态是当前唯一缺口。

### 20.3 未知 intent 字段在加载期报错

- `ContentDB.INTENT_KNOWN_FIELDS` / `INTENT_GAIN_STATUS_FIELDS` / `INTENT_ADD_CARD_FIELDS`
  是目标 schema 白名单；实现后需由加载校验和行为测试证明。
- `_validate_intent`：未知键直接报错；数值字段 ≥ 1；`gain_status.target`、
  `add_card.zone` 白名单；状态走 §20.2，牌走引用校验。
- 缺席特性（如「显式点名压力」）因此会**报错而不是静默降级**：写 `pressure_target` 是错的，
  想加它就必须先改引擎 + 这张表。

### 20.4 效果内选择张数

「至多 / 可选 0」使用显式 `min_count = 0` 表达；见[内容层契约 §7.5.2](内容层契约.md)。缺少选择能力时内容加载必须失败。


## 21. 人物被动 / 饰品 hook / 事件 op（扩展能力）

JSON 写法与语义见[内容层契约 §7.8](内容层契约.md)、§7.9；行为测试 `tests/suites/test_relic_hooks.gd`。

### 21.1 饰品 hook 执行目标

- `BattleCardRules.matched_relic_hooks(catalog, state, at, face)`：按 `at` + 卡过滤（`card_type` /
  `definition_id`）+ 回合过滤（`rounds`，验证整数后规范化为int）
  + 限次（`limit` → TriggerCounter `(per, "relic_hook:<ID>:<序号>", "hook")`）筛选，**只读不消费**。
- `BattleEngine._run_relic_hooks(ctx, at, face)`：先消费限次计数，再 `_run_effects_now(effects)`，
  并发 `relic_triggered{relic_id, hook_index, at}`。挂点：`_run_player_prepare`（round_start）、
  `_run_draw_phase`（draw，基础抽牌之后）、`_finalize_play`（card_resolved，进弃牌堆之后）。
- 费用类 hook 走报价路径：`relic_cost_hooks` 在 `cost_quote` 里算 `focus_discount` / `vitality_discount`
  并把 `matches` 交给 `_play_card` → `_consume_cost_sources` 在**出牌成功后**消费同一批计数
  （预览/预检反复调用报价不会消耗优惠；规则书 [ENG-003]；只有对应合法出牌提交才消费优惠）。
- 费用减免的目标模型是 `hooks[].at=cost_quote` 配合 `discount` 或 `skip_vitality_cost`，不使用 amount 0 的占位 effect；字段与限次语义已在内容§8冻结，接线在G2/G3验证。历史任务标签不作为规范引用。

### 21.2 人物被动 trigger

- `_handle_work_card_resolved` 泛化为「按 trigger 认牌型」：`work_card_resolved`（P01，计数键
  `work_resolved` 与行为都不变）/ `cooperation_card_resolved`（P04，计数键 `cooperation_resolved`）。
- 计数仍走 TriggerCounter `(round, passive.id, <trigger 键>)`，达到 `count` 后按 `limit` 触发一次。
- 备考面（`independent_answer`）只换合作牌正文、不换 `type`，因此照样计入一次合作牌结算（§3.4）。

### 21.3 事件 op（src/run）

- `gain_card.card_pool`：`_freeze_event_candidates` 把显式池原样冻结进 `EventState.frozen_candidates`
  （不抽随机），后续选择沿用现有 `selection_ids` 流程；`selection_count` 只支持 1（内容校验会拒绝 >1）。
- `remove_card.tag_filter` / `upgrade_card.type_filter`：`_remove_event_card` / `_upgrade_event_card`
  新增 `effect` 参数做目标过滤，非法目标返回 `INVALID_TARGET`（`error.event.card_tag_mismatch` /
  `error.event.card_type_mismatch`）；`_event_option_error` 的 dry-run 预检在**扣成本之前**跑完全部收益，
  所以非法选择不会扣钱/扣精力/删牌（「先校验、后提交」）。
- 视图：`options[].selection_candidates` 列合法卡实例 ID（升级按类型 + 未满级，删牌按 tag + 牌组下限），
  没有合法目标时 `enabled=false` 并在 `blocking` 给出 `error.event.no_remove_target` /
  `error.event.no_upgrade_target`。`candidates` 仍是卡定义 ID（gain_card 用），两者不混。
- A15 商店报价：`TransactionResolver.quote_price(run, stock)` 是唯一报价入口，`_prepare_buy` 用它算
  `plan.price`（`base_price` 另存），`_shop_view` 用它算展示价——界面标价与扣钱不可能不一致。
  餐食与删牌费不走这个函数（§8 A15：不影响删牌与餐食）。

普通屏障与查重护盾共存的消耗顺序 Q-007 只涉及完整版本，相关生产组合冻结前必须关闭；当前 MVP 不包含该定义。确定触发顺序只引用规则书 [RES-001]，首轮只引用 [INI-001]；先初始化、首次准备、开战即时、准备触发、基础抽牌、明确抽牌后效果。

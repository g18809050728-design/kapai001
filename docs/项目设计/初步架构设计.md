# 《交大四年：DDL战争》初步架构设计

版本：v0.1｜日期：2026-10-13｜状态：待实现的架构方案

模块调用契约见[接口文档](接口文档.md)。

内部职责见[类与方法设计](类与方法设计.md)，实体与持久化结构见[数据库与实体关系设计](数据库与实体关系设计.md)。本版数据库采用只读JSON内容库与本地聚合快照，ContentDB负责索引和引用校验。

## 1. 目标与范围

采用 **Godot 4＋GDScript的本地单体架构**，将战斗规则、局流程和界面表现分开。内容使用JSON配置，进度保存到本地文件。

首期目标是跑通一学期：选人物→地图→战斗/事件/商店/休息→考试首领→结算。具体MVP内容清单见[项目计划书](../../交大四年_DDL战争_项目计划书.md)，牌效和数值见[统一设计文档](../../交大四年_DDL战争_统一设计文档.md)。

优先满足三个要求：规则可以独立测试；动画不影响结果；退出后可以继续同一局。引擎具体版本在工程初始化时锁定。

## 2. 总体结构

```text
玩家操作
   ↓
UI：页面、卡面、目标选择、动画
   ↓ 操作请求                  ↑ 状态快照与事件
GameSession：协调当前局、战斗和页面切换
   ├── BattleEngine：战斗规则
   ├── RunService：地图、奖励、交易、成长
   └── SaveStore：保存与恢复
          
BattleEngine / RunService
   ├── ContentDB：只读内容定义
   └── RandomSource：可保存的随机状态
```

规则核心使用普通数据对象，不依赖Godot场景树、动画和音频。UI提交操作并展示结果，不能直接改精力、牌堆、金币或触发次数。

## 3. 模块职责

| 模块 | 负责 | 对外操作 |
|---|---|---|
| GameSession | 持有当前会话，协调流程与保存 | 新局、继续、提交操作、退出 |
| BattleEngine | 出牌、回合、状态、单位、场景、考试、胜负 | 开战、预览、出牌、确认选择、结束回合 |
| RunService | 地图、永久牌组、奖励、商店、事件、履历 | 进入节点、结算战斗、领取、购买、休息 |
| ContentDB | 加载并校验定义，筛选MVP内容 | 按ID查询、获取合法候选池 |
| RandomSource | 洗牌、掉落、事件和场景随机 | 抽取、导出/恢复随机状态 |
| SaveStore | 当前局、解锁和设置的文件读写 | 保存、读取、恢复备份 |
| UI | 页面、输入、提示与表现 | 渲染快照、发送操作请求 |

GameSession负责协调，不承包牌效和商店算法。初期在所属模块内用函数拆分；功能规模增长后再提取独立类。

## 4. 核心数据与归属

| 数据 | 主要字段 | 写入者 |
|---|---|---|
| ContentDef | 人物、卡牌、单位、场景、饰品、任务、事件定义 | ContentDB加载后只读 |
| RunState | 人物、难度、学期、节点、精力、钱、永久牌、饰品、履历、待领奖励 | RunService |
| BattleState | 回合、DDL、专注、精力、牌堆、状态、单位、任务阶段、场景、触发次数 | BattleEngine |
| Profile | 解锁、设置、教学记录、已结束局摘要 | GameSession调用存储更新 |

战斗期间精力以BattleState为准，RunState中的值仅为入场记录；战斗结束后一次性写回。抽弃牌不会修改永久牌组。

内容定义ID与运行实例ID分离：K01表示“写”的定义，同局多张K01各有实例ID。升级修改永久实例的升级等级；进入战斗时生成对应战斗实例，临时牌战后移除。

MVP与完整版本共用数据格式，用启用清单筛选内容；检查启用卡引用的单位、场景、事件奖励也已启用。

## 5. 核心流程

### 5.1 出牌

1. UI选择卡与必要目标，向BattleEngine请求预览；预览不改变状态或随机序列。
2. 引擎先解析考试替代面，再检查目标、费用、资源、单位容量与限次。
3. 校验通过后支付并执行效果，按明确顺序处理触发、暂离、转阶段和胜负。
4. 返回更新后的状态、表现事件，以及可能需要的后续选择。
5. 本次规则结算完成后保存稳定状态，UI播放动画。

支付前的目标或换班选择可以取消。抽牌后弃牌等效果内选择必须完成，不能撤销已揭示的抽牌结果；此时只允许提交当前选择。

操作带状态版本号，旧界面的重复请求拒绝执行。UI提交后锁定对应操作，防止连点重复支付。无效操作不改变资源或随机状态。

### 5.2 战斗回合

```text
准备 → 抽牌 → 玩家出牌 → 合作行动 → 弃牌
     → 敌方准备 → 敌方技能 → 敌方压力 → 轮末与DDL
     → 下一回合 / 胜利 / 失败
```

回合和胜负规则沿用统一设计文档。尤其保证：考试转换用于预览和实际执行的同一套逻辑；首领转阶段完成后才能判胜；最终任务完成立即结束；DDL超时不被精力救命效果抵消。

触发顺序显式写入规则代码，不依赖节点、字典或动画回调的遍历顺序。尚未确定的同窗优先级在实现相关牌时补充用例再确认。

### 5.3 局流程与交易

```text
选择人物 → 学期地图 → 节点处理 → 节点结算 → 学期地图
学期首领胜利 → 奖励与学期结算 → 下一学期
最终首领胜利 → 结局；战斗失败 → 本局总结
```

战斗结束返回结果，由RunService写回精力、生成奖励并推进节点。通过战斗ID和节点领取标记避免重复结算。

商店与事件先收集全部选择，再一次性校验并提交成本和收益。取消饰品替换不扣钱；奖励、库存和随机候选生成后保存，重新打开界面不重抽。

## 6. 内容与存档

### 内容配置

按人物、卡牌、单位、场景、饰品、状态、任务、事件分类保存JSON。卡牌至少包含ID、名称、类型、品质、费用、目标、效果、升级和耗尽标记。

常见效果用有限处理函数实现，如完成、压力、抽牌、放松、状态、召入单位、换场；复杂牌用专用函数组合，不先制作通用脚本语言或可视化编辑器。

加载时检查ID唯一、字段合法、引用存在、升级完整、MVP依赖齐全。JSON是实际运行来源；平衡调整同时更新统一设计文档。

### 保存与恢复

- 分别保存当前局、长期解锁和设置，存档包含格式版本、内容版本及随机状态。
- 当前局由SessionState统一保存RunState、可选BattleState及随机状态；revision只由会话层管理。结局先持久化待合并摘要，再按run_id幂等写入Profile，最后清除待合并标记。
- 在一张牌完整结算、节点操作完成等稳定边界保存；效果内选择未完成时先完成选择再保存退出。
- 战斗存档包含牌堆、任务阶段、意图、触发次数和场景已预抽结果，不能只保存血量与牌组。
- 先写临时文件并校验，再替换正式档，保留上一份有效备份；损坏时可恢复备份。
- 读档检查版本兼容，不能静默删除未知卡牌或重置当前局。

随机源按地图、奖励、事件、战斗分开，保存各自状态。预览和取消选择不消费随机；同版本、相同存档与操作应得到相同结果。

## 7. 工程目录规划

```text
src/
  app/          # GameSession、启动和页面协调
  battle/       # 战斗状态、回合、效果与目标处理
  run/          # 地图、奖励、交易、成长
  content/      # 定义加载、索引、校验
  storage/      # 存档、备份、版本处理
  common/       # 随机源等少量共享工具
  ui/           # 页面、卡面、单位、提示和动画
data/
  definitions/  # 分类内容JSON
  manifests/    # MVP与完整版本启用清单
assets/         # 人物、卡图、场景、图标、音频
tests/          # 规则、流程、存档和内容检查
docs/项目设计/  # 架构与导航
```

目录为拟建结构。先建立实际使用的文件，避免空模块和提前抽象。

## 8. 首期开发顺序与验收

| 顺序 | 工作 | 完成标准 |
|---|---|---|
| 1 | 内容加载、核心状态、随机源 | 定义可校验，实例可区分，随机可恢复 |
| 2 | 基础战斗 | K01/K02/K03与N01可完成一场战斗，非法操作无副作用 |
| 3 | 单位、场景、考试、阶段 | 护卫、换场、备考面、B01三阶段正确 |
| 4 | 战斗UI与存档 | 可交互出牌，退出继续结果一致 |
| 5 | 六节点局流程 | 奖励、商店、事件、休息和首领形成闭环 |
| 6 | MVP内容与教学 | 两人物完整试玩，再按反馈扩展内容 |

必要检查：统一文档T01～T20；交易取消及重复领取；预览无副作用；相同操作的连续运行与读档运行结果一致；开关动画不改变规则结果。

## 9. 关键取舍与待验证项

| 决策 | 理由与代价 | 重评条件 |
|---|---|---|
| 本地单体、核心与UI分离 | 适合单机小团队；需额外维护状态与展示转换 | 明确增加多人或在线功能 |
| JSON＋有限效果函数 | 便于调数值和检查；复杂牌仍需要代码 | 大量牌反复需要相同新增组合能力 |
| 稳定边界快照 | 恢复简单可靠；未完成选择不能保存半张牌 | 确实需要保存任意中间状态 |
| 同步规则、异步动画 | 结果稳定易测；长结算需要性能检查 | 实测单次结算影响交互 |

原型优先验证3专注经济、单位续航、考试转化效率和单学期时长。屏障细分、同窗触发排序等局部细节在对应功能实现前明确，不作为本次初步架构额外改写玩法。

# 战斗界面契约（src/ui/battle_screen.gd + src/ui/battle/**）

> 实现来源：《初步架构设计》§2「UI 提交操作并展示结果，不能直接改精力、牌堆、金币或触发次数」、
> 《战斗模块契约》§7～§10。本文件是该模块对外的唯一契约说明；变更必须同步
> `tests/suites/test_ui_battle_screen.gd` 与 `tests/suites/test_ui_battle_choice.gd`。

## 1. 文件与职责

| 文件 | 职责 |
|---|---|
| `src/ui/battle_screen.tscn` / `battle_screen.gd` | 战斗画面（页面的唯一入口，class_name `BattleScreen`） |
| `src/ui/battle/battle_session.gd` | 会话：持有 engine + state + rng_state，只调 begin/preview/apply/make_view |
| `src/ui/battle/battle_event_animator.gd` | 事件动画队列（只影响观看节奏） |
| `src/ui/battle/battle_card_widget.gd` | 手牌卡面（费用 / 类型 / 完成量或放松 / 升级后数值） |
| `src/ui/battle/battle_task_card.gd` | 任务卡（进度、屏障、公开意图、阶段） |
| `src/ui/battle/battle_unit_slot.gd` | 单位槽（精力、协作、放松、护卫、协作目标） |
| `src/ui/battle/battle_log_panel.gd` | 结算日志（每行都来自引擎事件或 BattleOutcome） |
| `src/ui/battle/battle_choice_panel.gd` | 效果内选择面板（K03 抽 2 弃 1） |
| `src/ui/battle/battle_deck_viewer.gd` | 牌堆查看弹窗 |
| `src/ui/battle/battle_rules_dialog.gd` | 规则说明弹窗 |
| `src/ui/battle/battle_labels.gd` / `battle_style.gd` | 展示层文案表 / 配色与控件工厂 |

## 2. 页面入口（ui-shell 对接）

```gdscript
var screen = preload("res://src/ui/battle_screen.tscn").instantiate()
add_child(screen)
screen.start_battle(battle_input)        # RunService 的 battle_input 原样传入，返回 Result
screen.battle_finished.connect(_on_battle_finished)   # 载荷就是 BattleOutcome
```

| 成员 | 说明 |
|---|---|
| `start_battle(battle_input) -> Result` | 开战；`battle_input` 字段见《战斗模块契约》§2。目录清单默认 `battle_mvp`，载入失败回落 `mvp` |
| `set_engine(engine)` / `prepare()` | 复用上层已载入的引擎 / 提前建好界面（要在 `start_battle` 前设动画开关时用） |
| `signal battle_finished(outcome)` | 打出 BattleOutcome 时发出，`outcome` 就是 `BattleStep.outcome` |
| `signal action_applied(step)` / `view_updated(view)` | 每次成功提交后的 BattleStep / 刷新后的视图 |
| `current_state()` | 交给 `RunService.settle_battle(state, outcome, rng_states)` 写回的战斗状态 |
| `current_rng_state()` | 战斗随机流快照；整份会话随机快照由上层维护，界面不做合并 |
| `is_locked()` / `is_finished()` / `outcome()` | 界面状态查询 |

## 3. 界面只消费视图（不得重算规则）

界面只读两类数据源：

1. `BattleEngine.make_view(state) -> BattleView`（字段见《战斗模块契约》§8）；
2. `BattleEngine.preview(state, draft) -> ActionPreview` 的 `can_submit` / `required_selections` / `blocking_errors`。

卡面费用取 `hand[].effective_cost`，可出性取 `hand[].playable`，效果数值取 `hand[].face.effects`
（已含升级与考试替代面）。界面对任何非法操作只显示 `blocking_errors` 的 message_key，
不自己判断合法性。

`BattleSession` 连日志要用的名字与任务进度也从视图取（`hand[]` / `zones_public` / `tasks[]` / `units[]`），
不读 BattleState 的字段——这样规则层改字段不会悄悄影响界面。

## 4. 动作协议

`build_action(type, params) -> {type, payload}` 是界面上唯一的动作生产函数：

| type | payload | 界面触发点 |
|---|---|---|
| `play_card` | `card_id`、`target_ids`、`replace_unit_id`（无则 null） | 点手牌 → （需要时点任务 / 单位）→ 自动提交 |
| `confirm_choice` | `choice_id`、`selected_ids` | 待选面板的确认按钮 |
| `set_ally_target` | `unit_id`、`task_id` | 点单位 → 点任务 |
| `end_turn` | `retained_card_ids` | 结束回合按钮 |

提交路径唯一：`BattleScreen._submit()` → `BattleSession.submit()` → `BattleEngine.apply(state, action, rng_state)`。
界面没有任何一处直接写精力、牌堆、金币或触发次数。

## 5. 效果内选择（pending_choice）期间的锁

`view.pending_choice != null` 时：

- `build_action` 对除 `confirm_choice` 外的一切类型返回**空字典**（调用方拿不到可提交的动作）；
- 手牌、任务、单位、结束回合、牌堆、规则说明、动画开关、取消选择全部禁用；
- 非法确认（数量不符 / 非候选 / 重复）由引擎拒绝，界面保持待选并显示原因；
- 待选的候选就是引擎给的 `pending_choice.candidates`，界面不自己凑候选。

锁快照可用 `lock_snapshot()` 断言。

## 6. 动画：只影响观看节奏

`BattleEventAnimator` 只做一件事：把 `BattleStep.events` 按时间播出来（`base_delay` / `speed_scale`）。
它不持有也不需要 BattleState，因此：

- 关闭动画（`animation_enabled = false`）= 事件立即播完；
- 加速（`speed_scale` 变大）= 同样的事件更快播完；
- 两者都不改变视图、日志、结局或随机快照，`test_ui_battle_choice.gd` 用「两组输入序列 + 最终视图 + 日志 + 结局逐项相等」钉死这点。
- 顶栏「动画：开/关」按钮只切 `animation_enabled`；待选期间该按钮同样被锁。

日志不走动画：结算日志在每次 `render(view)` 时整体刷新，避免测试与读档依赖播放进度。

## 7. 牌堆查看的公平性

- 抽牌堆：**只显示数量**，不展示内容与顺序（`draw_pile_card_ids()` 恒为空，供测试钉死）；
- 弃牌堆 / 消耗堆：内容来自 `BattleView.zones_public`（公开信息），卡面与 `hand[]` 同构；
- `draw` 与 `resolving` 不进入 `zones_public`；
- 弹窗不洗牌、不改状态；待选期间不允许打开。

## 8. 冒烟测试

`tests/suites/test_ui_battle_screen.gd`：实例化 `battle_screen.tscn`、注入输入、断言视图与状态一致，
并用界面 API 从零打完 N01（覆盖 K03 的抽后弃牌），断言 `outcome = won / tasks_completed`。

`tests/suites/test_ui_battle_choice.gd`：动画队列本体、K03 待选细节与非法确认、目标选择与取消、单位槽换班、动画不变性。

两个套件都用 `Engine.get_main_loop()` 拿 SceneTree 挂场景，随 `tests/run_tests.gd` 一起跑。

## 9. 内容清单策略（t12 之后）

界面自己载清单时的顺序：`manifest_id`（默认 `mvp`，与出厂局流程一致）→ `battle_mvp`，第一个载入成功的就用。

**不能用 `battle_mvp` 当默认**：它冻结在 12 张牌的旧战斗切片，而出厂 `mvp` 清单里已经有 K05/K06/K07/K08/K10/K12/K15/K16/K19/K59/K60/K45/K52/X01 等牌。
局流程一旦把含这些牌的牌堆交给界面，用 battle_mvp 载入的 catalog 会在 `engine.begin` 直接报 `unknown_card`，战斗根本开不起来。
回归断言见 `test_ui_battle_screen.gd` 的「界面：出厂 mvp 清单下的牌堆」一节。上层若已载入 catalog，直接 `set_engine(engine)` 即可，界面不会重复载。

**出厂局流程走的是注入路径**：`main.gd` 找到 `res://src/ui/battle_screen.tscn` 后调 `GameShell.attach_battle_host(screen)`，其中包含 `set_engine(BattleEngine.new(局的 catalog))`，因此真实对局里界面用的是「局自己那份 catalog」，上面这条回落链只服务于界面独立运行与冒烟测试。接线只有 `attach_battle_host` 一处，界面 API 变更时改那一处即可。

### 9.1 代价显示：专注与精力

t12 起 `cost_quote` 返回 `vitality_base / vitality_discount / vitality_cost`，`make_view.hand[]` 对应 `effective_vitality_cost`，`preview.costs.vitality` 与之同源。界面据此显示：

- 卡面第一行左侧是专注费用（`effective_cost`，蓝色大号），右侧单列精力代价（`effective_vitality_cost`，红色小号，为 0 时隐藏）；
- 提示词同时列出两种代价，并注明精力是「主动支付，绕过放松」；
- 精力不足时由 `preview` / `apply` 拒绝，界面显示「精力不足：需要 N，且支付后至少留 must_keep」。

界面**不自己判断**精力够不够（那要读 `minimum_vitality_after_payment` 规则）：`hand[].playable` 只反映专注与「不可打出」标记，最终以 `preview.can_submit` 为准。


## 10. 边界（不做什么）

> 本节原为 §9，2026-10-14 t12 之后顺延为 §10。

- 不改 `src/battle`、`src/storage`、`src/run` 的规则语义；视图缺字段就报给队长加受控修复任务；
- 不实现局流程页面（主菜单 / 地图 / 奖励 / 商店等属 `src/ui/page_*.gd`，由 ui-shell 负责）；
- `project.godot` 的 `main_scene` 仍由 ui-shell 的入口决定；战斗页面只被实例化。

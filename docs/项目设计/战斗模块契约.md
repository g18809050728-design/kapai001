# 战斗模块契约（src/battle/**）

> 实现来源：《接口文档》§4、《类与方法设计》§3、《游戏规则书》§3.3～§10。
> 本文件是该模块对外的唯一契约说明；字段含义与取值范围以此为准。
> 变更本文件必须同步 `tests/suites/test_battle_*.gd`。

## 1. 入口

```gdscript
var engine := BattleEngine.new(content_db)   # 只读内容库，可空后再 set_catalog()
engine.begin(input) -> Result<BattleStep>
engine.preview(state, draft) -> Result<ActionPreview>
engine.apply(state, action, rng_state) -> Result<BattleStep>
engine.make_view(state) -> BattleView
engine.resolve_face(state, card_id) -> Result<EffectiveCard>
engine.calculate_cost(state, card_id) -> Result<CostQuote>
```

- `preview` / `calculate_cost` / `make_view` 不改变状态、不消费随机。
- `apply` 在 `state.copy_for_write()` 的工作副本上结算：失败返回 `Result.fail`，调用方状态不变。
- `apply` 的 `rng_state` 传当前战斗随机快照；不传则用零种子（仅测试便利，生产必须显式传）。

## 2. BattleInput（begin 入参，Dictionary）

| 字段 | 类型 | 说明 |
|---|---|---|
| battle_id | String | 战斗实例 ID；为空时回落 `battle#1`，也是战斗内自造 ID 的前缀 |
| node_id | String | 地图节点，可空 |
| encounter_id | String | 遭遇定义 ID（必填，必须在清单内启用） |
| character_id | String | 人物定义 ID，用于 P01 被动等 |
| difficulty | String | relaxed / normal / hard；取 `difficulty_overrides` |
| vitality | int | 入场当前精力，缺省为 max_vitality |
| max_vitality | int | 入场最大精力，缺省为 `run.starting_vitality` |
| cards | Array | 永久牌实例快照：`{card_id, definition_id, origin_card_id, upgrade_level}`；全部进抽牌堆后洗牌 |
| relics | Array | 已装备饰品定义 ID（如 `["A01"]`） |
| rng_state | Dictionary | 战斗随机流快照（`RandomSource.export_state()`），可空 |

### 2.1 `relics` 的前置约定（t18 补充）

`BattleInput.relics` 必须是**当前清单内已启用**的定义 ID（内部按 `slot` 排序，传参顺序不影响结算）。

原因：饰品收益自 t10 起是**数据驱动 hook**（`data/definitions/relics.json` 的 `effects` / `hooks`）。
遇到未启用或未定义的定义，hook 只是**不生效**、不会报错。典型例子是 A04（每战首张合作牌费用 -1）：
清单里没启用 A04 时它静默失效，调用方只会看到「费用没减」，很难反查到是清单问题。

生产路径天然满足：`RunService._battle_input` 从本局的饰品实例生成这份列表。**手写 battle_input 的测试与工具必须自己保证**：

```gdscript
for relic_id in input.get("relics", []):
    # 只做自查；未启用时应显式失败，而不是让 hook 静默跳过
    assert(db.is_enabled(GameConstants.KIND_RELIC, String(relic_id)))
```

**待评估项（本任务只记录，未实现）**：是否在 `BattleEngine.begin()` 对 `relics`（以及 `cards[].definition_id`、
`encounter.tasks` 引用的内容）做一次加载期校验，宁可**响亮失败**。

- **建议：值得做**，但只覆盖「调用方直接塞进来的 ID 列表」（`relics` / `cards`），范围可控；
- 收益：把「静默不生效」变成 `CONTENT_INVALID`，避免界面与测试把「规则根本没跑」误判成「数值不对」；
- 代价：① 只是遍历一下列表，开销可忽略；② **会改变现有语义**——传了清单外 ID 的既有调用点会从「静默通过」变成「失败」，
  落地前需要先扫一遍测试与工具里的手写 `battle_input`；③ 错误码与返回形状复用现有的 `Result.fail(CONTENT_INVALID, ...)`，不需要新增；
- 不做也能接受：唯一的生产来源是 `RunService._battle_input`，手写输入只出现在测试与诊断工具里。

## 3. BattleStep（begin/apply 返回）

| 字段 | 类型 | 说明 |
|---|---|---|
| state | BattleState | 工作副本，成功时才是可发布的新状态 |
| events | Array<RuleEvent> | 本次增量事件；见 §6 |
| pending_choice | ChoiceRequest 或 null | 效果内选择；非空时必须先 confirm_choice |
| outcome | BattleOutcome 或 null | 非空表示战斗已结束 |
| stable | bool | `pending_choice == null and outcome == null` |
| rng_state | Dictionary | 本次执行后的战斗随机快照；与状态共同提交或共同回滚 |

BattleOutcome：`{battle_id, result, reason, remaining_vitality, summary}`；
`result ∈ won/lost/abandoned`，`reason ∈ tasks_completed/vitality_depleted/deadline_expired`。

## 4. 相位机

显式顺序（`BattleEngine.PHASE_ORDER`），不依赖字典遍历：

```text
player_prepare -> draw -> player_action -> ally_action -> discard
  -> enemy_prepare -> enemy_skill -> enemy_pressure -> round_end
  -> （round_index+1、推进意图）player_prepare ...
```

- `begin` 自动推进到第一个 `player_action`（或待选/终局）。
- `end_turn` 从 `player_action` 连续推进到下一轮 `player_action`。
- `apply(play_card)` 只结算该牌，不自动结束回合。
- `awaiting_choice` 是待选暂停态；`finished` 后由 `outcome` 说明结果。

## 5. 结算约定（实现已锁定）

- 完成量：`max(0, 基础 + 适用固定加值 - 惩罚)`，先扣任务屏障，再减未完成量，不结转超额。
- 压力：先扣放松，再减精力；主动支付精力绕过放松。
- 费用：`max(0, 基础费用 + 加费 - 减费)`；一次性优惠在对应合法出牌成功后消费。
- DDL：还能经历的轮末次数；最后一任务完成立即胜利，不再扣 DDL；扣到 0 仍有任务则 `deadline_expired`。
- 阶段转换：旧阶段归零先生成新 `task_id`，旧目标多段跳过，不提前判胜。
- 随机：只有 `RandomSource` battle 流被本模块推进；preview 与失败操作不消费随机。

## 6. RuleEvent（events 元素）

每个事件为 `{"type": String, ...载荷}`。稳定类型：

`phase_changed`、`round_started`、`focus_changed`、`card_played`、`card_resolved`、
`card_drawn`、`card_discarded`、`choice_requested`、`choice_confirmed`、`status_gained`、
`status_removed`、`completion_applied`、`pressure_applied`、`vitality_changed`、
`unit_summoned`、`unit_departed`、`scene_established`、`scene_replaced`、
`task_advanced`、`task_completed`、`enemy_skill`、`ddl_ticked`、`battle_finished`、
`coop_target_set`。

事件常量在 `BattleEngine.EVENT_*`；UI 只读，不得据此修改规则状态。

## 7. Action 与 ChoiceRequest

Battle 动作沿用 `GameAction = {type, payload}`：

| type | payload |
|---|---|
| play_card | card_id、target_ids、replace_unit_id（可空） |
| confirm_choice | choice_id、selected_ids |
| set_ally_target | unit_id、task_id |
| end_turn | retained_card_ids |

ChoiceRequest：`{choice_id, kind, prompt_key, candidates:[{id,label_key,preview}], min_count, max_count, source_card_id}`。

## 8. BattleView（make_view）

顶层：`battle_id/node_id/encounter_id/phase/round_index/ddl/character_id/difficulty/
relics/exam_limits/player/hand/zones/units/tasks/statuses/scene/pending_choice/outcome/
stable/phase_order`。

- `player`：`{entity_id, vitality, max_vitality, relax, focus}`
- `hand[]`：`{card_id, definition_id, origin_card_id, upgrade_level, effective_cost, playable, face}`
- `zones`：五区计数 `{draw, hand, discard, exhaust, resolving}`
- `tasks[]`：`{task_id, definition_id, phase_key, work_remaining, work_max, shield, entered_order, eligible_round, intent}`
- `scene`：`{scene_id, definition_id, established_round, pending_random_result}` 或 null

## 9. 战斗内实例 ID 与触发计数

- 战斗内自造实例 ID = `<battle_id>|<prefix><n>`（prefix：p/t/u/s/c/st/ch），单调不复用、不消费随机；
  永久牌实例 ID 仍由 `RunState` 分配并作为 `BattleCard.origin_card_id`。
- 触发计数键 = `BattleState.counter_key(scope, owner_key, trigger_key)`，
  `scope ∈ round / instance_round / battle`（`GameConstants.COUNTER_SCOPE_*`）。
  回合类计数在玩家准备阶段重置；实例限次的 `owner_key` 用 `origin_card_id`，换场/回收不刷新。
- `TaskState.intent_snapshot` 为当前公开意图的 Dictionary 副本；`intent_cursor` 每轮末 +1。

## 10. 效果内选择（步骤 2）

- K03「抽2弃1」：`draw` 先执行，随后 `discard` 产生 `pending_choice`；
  候选 = 抽牌之后的手牌（含新抽到的牌），`min_count = max_count = 1`。
- 待选期间 `state.resolution != null` 且 `phase = awaiting_choice`：
  `play_card` 与 `end_turn` 一律返回 `CHOICE_PENDING`；`confirm_choice` 数量/候选非法时
  返回 `INVALID_ARGUMENT` / `INVALID_TARGET` 且**不清除原待选**。
- 未提交 = 未支付：`preview` 与任何被拒绝的 `apply` 都不扣专注、不移牌、不消费随机。
  一旦支付并进入待选，按 [PLY-002] 不能取消整张牌。
- `ResolutionState.choice` 是待选真相（跨调用保留在 state 里）；`BattleStep.pending_choice`
  是同一份数据快照。

## 13. 单位（步骤 3）

数据：`data/definitions/units.json`，字段 `id / name_key / vitality / cooperation / guard / support / entry_effects`。

- 召入：`summon_unit` → 检查 `battle.unit_slots`；满槽时必须提供 `replace_unit_id`，否则 `INVALID_TARGET`
  （取消 = 不提交，不扣费、不移牌）。
- 换班：旧单位移出（原因 `switch`）→ 新单位进入并分配新 `entered_order`；不触发暂离奖励。
- 暂离：精力归零立即移出（原因 `exhausted`），其状态一并移除。
- 合作阶段：按 `entered_order` 升序，每个单位每回合最多一次——
  支援（`support`）→ 协作完成（`cooperation`）→ 自身失去 `battle.unit_action_vitality_cost` 精力（绕过放松）。
  协作目标优先 `UnitState.target_id`，失效回退行动顺序最前任务；完成最后任务立即胜利并停止后续步骤。
- `support.kind`：`relax / self_relax / cleanse_or_relax / gain_status_on_actions / heal`。
- `guard=true` 的单位入场即获得护卫状态。

## 14. 护卫与压力改向

- 默认单体压力目标 = 最早入场的存活护卫（`entered_order` 最小），否则主角。
- 每段压力重新选目标；伤害不溢出：目标精力归零立即暂离，剩余伤害不转给主角。
- 全体压力（`pressure_all`）与显式点名不经过护卫改向。

## 17. 多阶段任务与转阶段

- `TaskState` 由 `(definition_id, phase_key)` 定位，`phases` 顺序推进。
- 阶段归零：**先**生成下一阶段的新 `task_id`（清旧屏障与状态，旧 task_id 不再存在），**再**由调用方在完整连锁结束后判定胜负，不提前胜利。
- 旧目标多段：`ResolutionState.locked_target_ids` 指向旧 task_id 时，后续段**直接跳过**（不结算、不改任何 task）。
  这条由 `_primary_task` 的两个分支保证，别把它们合并：
  - **给了锁定目标、但目标已不存在或已归零** → 返回 `null`，本段完成量丢弃（若回退到新阶段，等于替玩家白打一个阶段，且悄无声息）；
  - **本来就没给目标**（场景 / 单位 / 饰品效果传空数组）→ 才回退到首个合法任务。
  现役牌面都是单段 `complete`，回归用例用合成两段队列构造跨阶段场景：`tests/suites/test_phase_segments.gd`。
- `eligible_round`：玩家侧阶段生成的任务当轮可行动；敌方行动中生成的新任务 `eligible_round = round_index + 1`。
- 新阶段不承接旧阶段超额完成量（`work_remaining` 由新阶段 `work_max` 重置）。

### 19.1 效果内选择（一次只允许一个待选）

- 三个 kind 共用同一套机制：`ResolutionState.choice` 是唯一真相，`BattleStep.pending_choice` 是它的快照；
  `kind ∈ discard / recall / purify`（`GameConstants.CHOICE_*`），候选统一为 `{id, label_key, preview}`。
- `_execute_queue` 遇到需要选择的 op 就调 `_start_effect_choice` 并**立刻返回**（`phase = awaiting_choice`）；
  `_confirm_choice` 校验数量/候选后追加 `choice_counts[kind] = 实际生效数量`、游标 +1，再继续队列。
  因此同一时刻只可能有一个待选：待选期间 `play_card` / `end_turn` 都是 `CHOICE_PENDING`，
  K03 的「抽后弃」与 K07/K12 的新选择天然串行，不会互相插队。
- 待选请求新增字段 `effect_amount`（该效果的 `amount`，如净化层数）；`preview` 里带各自的上下文
  （角色/状态 id + 层数）。
- 需要选择的 op 只能写在卡牌效果里（内容校验强制）：场景/饰品/被动/单位支援没有挂起再回来的上下文。

### 19.2 其它引擎增量

- `pre_effects` 从「只有建立场景时执行」改为**整张牌结算前执行一次**（`_play_card`），
  基础定义与 `upgrade` 都支持；考试替代面清空 `pre_effects`。K52/K53 的「建立前」时序不变。
- 保留手牌真正落地：此前 `end_turn` 只校验 `retained_card_ids` 而弃牌阶段仍弃掉全部手牌；
  现在保留牌在弃牌阶段被跳过，`BattleState.retained_card_ids` 读完即清空（不写入稳定快照）。
- 新增 RuleEvent：`card_recalled` / `retention_granted`。
- X01 依赖：`N03`（C语言练习）意图 B 的 `add_card {card: X01, zone: discard}` 现在能通过引用校验
  （X01 已在 `mvp.json` 启用）。N03 自身进清单由内容侧决定。
- `X01.rarity = null`：奖励/商店池按品质过滤，特殊牌因此不进普通随机池
  （《游戏规则书》「基础/特殊牌不进普通随机池」）；不需要改 `src/run` 的池逻辑。


## 20. 受控修复 t12：消除静默失败

来源：verifier 的 t5 审查（3 条刻意红的偏差探针）。三条修复都是同一句话：
**引擎不会做的事，不许被静默忽略或近似掉**。JSON 写法见[常量与规则配置](常量与规则配置.md)§6、§7。

### 20.1 主动支付精力（F1，[ENG-003] / RB-03 / T03）

- `BattleCardRules.resolve_face` 把 `vitality_cost` 带进卡面（基础 + `upgrade` 覆盖，都是 int）。
- `cost_quote` 返回 `vitality_base / vitality_discount / vitality_cost`；`vitality_cost` 不再硬编码 0，
  减免源（A08，t10）接在 `vitality_discount` 上。
- `validate_play`：`精力 - vitality_cost >= battle.minimum_vitality_after_payment`（配置键不再悬空），
  不足返回 `INSUFFICIENT_RESOURCE` / `error.play.not_enough_vitality`，且在任何写入之前返回
  （不扣费、不移牌、不推进随机、不加计数）。
- `_play_card`：与专注费同一步支付，直接扣 `player.vitality` 并发 `vitality_changed{paid}`；
  绕过放松（与压力伤害不同）。`make_view.hand[].effective_vitality_cost` 与 `preview.costs.vitality` 同源。
- 内容侧撤回 K10 的近似：`{"op": "lose_vitality", "amount": 4}` → `"vitality_cost": 4`（升级 3），
  `effects` 只剩 `gain_focus 2`。`lose_vitality` 保留给真正的伤害（L06 轮末、事件支付）。

### 20.2 未接线状态在加载期被拒（F2）

- 新增 `GameConstants.WIRED_STATUS_IDS`（引擎真会结算的状态清单）与
  `ContentDB.UNWIRED_STATUS_GAPS`（未接线 → 缺什么）。
- `ContentDB._check_status_wiring` 挂在 `_validate_effect_list`（卡牌/饰品/场景/单位/被动/upgrade
  全覆盖）与 intent 的 `gain_status` 上：未接线或未定义一律 `CONTENT_INVALID`，消息写出缺口。
- 当前唯一未接线状态是 `plagiarism_shield`（缺屏障吸收结算）。**实现它之前，内容里写不进去**——
  这就是这条闸门存在的意义：宁可加载失败，也不让内容作者以为它生效了。

### 20.3 未知 intent 字段在加载期报错（F3）

- `ContentDB.INTENT_KNOWN_FIELDS` / `INTENT_GAIN_STATUS_FIELDS` / `INTENT_ADD_CARD_FIELDS`
  是权威字段集（读取处：`_run_enemy_skill` / `_run_enemy_pressure` / `_intent_holder`）。
- `_validate_intent`：未知键直接报错；数值字段 ≥ 1；`gain_status.target`、
  `add_card.zone` 白名单；状态走 §20.2，牌走引用校验。
- 缺席特性（如「显式点名压力」）因此会**报错而不是静默降级**：写 `pressure_target` 是错的，
  想加它就必须先改引擎 + 这张表。

### 20.4 效果内选择张数（F4）

「至多 / 可选 0」由 t9 的 `discard.up_to` 覆盖（`min_count = 0`，见
[常量与规则配置](常量与规则配置.md)§5.2 与 `tests/suites/test_battle_ops.gd`），本任务只做回归确认。


## 21. 人物被动 / 饰品 hook / 事件 op（步骤 4 / 引擎增量二，t10）

JSON 写法与语义见[常量与规则配置](常量与规则配置.md)§8、§9；行为测试 `tests/suites/test_relic_hooks.gd`。

### 21.1 饰品 hook 执行器

- `BattleCardRules.matched_relic_hooks(catalog, state, at, face)`：按 `at` + 卡过滤（`card_type` /
  `definition_id`）+ 回合过滤（`rounds`，按整数比——JSON 数字是 float，`Array.has(3)` 对 `[3.0]` 是 false）
  + 限次（`limit` → TriggerCounter `(per, "relic_hook:<ID>:<序号>", "hook")`）筛选，**只读不消费**。
- `BattleEngine._run_relic_hooks(ctx, at, face)`：先消费限次计数，再 `_run_effects_now(effects)`，
  并发 `relic_triggered{relic_id, hook_index, at}`。挂点：`_run_player_prepare`（round_start）、
  `_run_draw_phase`（draw，基础抽牌之后）、`_finalize_play`（card_resolved，进弃牌堆之后）。
- 费用类 hook 走报价路径：`relic_cost_hooks` 在 `cost_quote` 里算 `focus_discount` / `vitality_discount`
  并把 `matches` 交给 `_play_card` → `_consume_cost_sources` 在**出牌成功后**消费同一批计数
  （预览/预检反复调用报价不会消耗优惠，符合 [ENG-003]「取消预选不消耗优惠」）。
- A04 的硬编码分支已删除：费用减免现在是 `hooks[].at=cost_quote + discount`，`relics.json` 里不再有
  amount 0 的占位 effect。A08 用同一个时点的 `skip_vitality_cost` 接在 t12 预留的 `vitality_discount` 上。

### 21.2 人物被动 trigger

- `_handle_work_card_resolved` 泛化为「按 trigger 认牌型」：`work_card_resolved`（P01，计数键
  `work_resolved` 与行为都不变）/ `cooperation_card_resolved`（P04，计数键 `cooperation_resolved`）。
- 计数仍走 TriggerCounter `(round, passive.id, <trigger 键>)`，达到 `count` 后按 `limit` 触发一次。
- 备考面（`independent_answer`）只换合作牌正文、不换 `type`，因此照样计入一次合作牌结算（§3.4）。

### 21.3 事件 op（src/run）

- `gain_card.card_pool`：`_freeze_event_candidates` 把显式池原样冻结进 `EventState.frozen_candidates`
  （不抽随机），后续选择沿用现有 `selection_ids` 流程；`selection_count` 只支持 1（内容校验会拒绝 >1）。
- `remove_card.tag_filter` / `upgrade_card.type_filter`：`_remove_event_card` / `_upgrade_event_card`
  新增 `effect` 参数做目标过滤，非法目标返回 `INVALID_TARGET`（`error.event.card_tag_mismatch` /
  `error.event.card_type_mismatch`）；`_event_option_error` 的 dry-run 预检在**扣成本之前**跑完全部收益，
  所以非法选择不会扣钱/扣精力/删牌（「先校验、后提交」）。
- 视图：`options[].selection_candidates` 列合法卡实例 ID（升级按类型 + 未满级，删牌按 tag + 牌组下限），
  没有合法目标时 `enabled=false` 并在 `blocking` 给出 `error.event.no_remove_target` /
  `error.event.no_upgrade_target`。`candidates` 仍是卡定义 ID（gain_card 用），两者不混。
- A15 商店报价：`TransactionResolver.quote_price(run, stock)` 是唯一报价入口，`_prepare_buy` 用它算
  `plan.price`（`base_price` 另存），`_shop_view` 用它算展示价——界面标价与扣钱不可能不一致。
  餐食与删牌费不走这个函数（§8 A15：不影响删牌与餐食）。

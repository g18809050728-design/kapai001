# 局流程契约（src/run/**、src/app/**）

> 实现来源：《接口文档》§5、《类与方法设计》§4、《统一设计文档》§10、《数据库与实体关系设计》§5/§7/§9。
> 本文是 **RunService 对外契约的唯一说明**：签名、RunStep 字段、节点推进规则、幂等键、错误码。
> 变更本文件必须同步 `tests/suites/test_run_service.gd`。验证命令见 README（退出码 0 才算过）。

## 1. 入口

```gdscript
var svc := RunService.new(content_db)   # 只读内容库，可空后再 set_catalog()
svc.create(request, profile) -> Result<RunStep>
svc.preview(state, draft) -> Result<ActionPreview>
svc.apply(state, action, rng_states) -> Result<RunStep>
svc.settle_battle(state, outcome, rng_states) -> Result<RunStep>
svc.make_view(state) -> RunView
svc.eligible_endings(state) -> Array[String]
svc.rewards() -> RewardGenerator          # 只读候选/商店生成器
svc.transactions() -> TransactionResolver # 只读交易计划器（preview 复用）
```

`request = {character_id, difficulty, manifest_id, seed}`（接口文档 §2；seed 为十进制字符串，也接受整数）。
`profile` 只读，RunService 只读 `profile.unlocked_ids`。
`rng_states` 是 `RandomSource.export_state()` 的完整快照（四条流）；不传表示从零种子开始（仅测试便利）。

## 2. RunStep

| 字段 | 类型 | 说明 |
|---|---|---|
| state | RunState | 本次命令后的**工作副本**，成功时才是可发布的新状态 |
| events | Array<RuleEvent> | 本次增量事件，`index` 从 0 递增 |
| battle_input | Dictionary 或 null | 进入战斗节点时给出，可直接交给 `BattleEngine.begin()` |
| run_summary | RunSummary 或 null | 只在**本步产生结局**时非空（对象，不是 Dictionary） |
| rng_states | Dictionary | 本次执行后的完整随机快照；与状态共同提交或共同回滚 |

`battle_input`（战斗模块契约 §2）：`{battle_id, node_id, encounter_id, character_id, difficulty,
vitality, max_vitality, cards, relics, rng_state}`。
- `battle_id == node_id`（一个战斗节点只有一场战斗），也是结算幂等键。
- `cards[] = {card_id, definition_id, origin_card_id, upgrade_level}`：`card_id` 就是永久牌实例 ID，
  `origin_card_id` 指向同一实例（本局一张永久牌同时只在一场战斗中）。
- `relics` 是按 slot 升序的饰品**定义 ID** 数组。
- `rng_state` = 本次命令提交后的完整快照（含刚推进的 map/reward/event 流）。

`ActionPreview`（接口文档 §3.3）：`{revision(占位 0，由会话层填), can_submit, required_selections,
costs, known_effects, unknown_effects(null), effective_card(null), blocking_errors[]}`；
`blocking_errors[] = {code, message_key, details}`。preview 不改状态、不消费随机。

## 3. RunState 增补字段（《数据库与实体关系设计》§5）

| 字段 | 说明 |
|---|---|
| nodes | `Array[RunNodeState]`：整局地图骨架（确定性生成，见 §4） |
| current_node_id | 已进入、尚未完成的节点；空串表示在学期入口 |
| node_path | 已完成节点 ID 顺序（整局累计，换学期清空） |
| pending_reward | 当前待处理 `RewardOffer`（战斗胜利后生成）；处理完才能离开节点 |
| settlement | 当前 `TermSettlement`；步骤全部完成后推进到下一学期 |
| run_summary | 局结束时生成的 `RunSummary`（对象） |
| pending_profile_summary | 与 run_summary 同一对象（或都为 null），供存档层三步提交后清空 |
| seen_event_ids | 已出现（含离开）的事件定义 ID；同局同 ID 至多一次 |
| removals_used | 全局删牌次数：商店删牌价格 = first_removal_price + increment × 本值；事件删卡不计数 |
| career_direction | 第 5 学期开始前选择的履历方向（research/competition/internship） |
| active_battle_id / active_encounter_id | 已进入、尚未结算的战斗；非空时 RunService 拒绝一切写操作 |
| outcome | `""` / `won` / `lost` / `abandoned` |

实体类：`RunNodeState`、`RewardOffer`、`ShopState`、`EventState`、`TermSettlement`、`RunSummary`（均 `src/run/**`）。
子实体一律走静态工厂 `X.create(...)`；跨脚本不要写 `Outer.Inner.new()`（Godot 不暴露该路径）。
`RunState.copy_for_write()` 是深拷贝（所有嵌套容器与子实体），「非法操作不改变状态」靠它保证。

## 4. 地图与节点推进规则

**模板**（《统一设计文档》§10）：每学期 6 层，第 2、4 层是二选一分支，所以每学期生成 **8 个 NodeState**：

| 层 | 节点 | 数量 |
|---|---|---|
| 1 | normal 普通作业 | 1 |
| 2 | event 事件、normal 普通作业 | 2（二选一） |
| 3 | shop 商店 | 1 |
| 4 | normal 普通、elite 精英 | 2（二选一，保证不打精英的通路） |
| 5 | rest 休息 | 1 |
| 6 | boss 首领 | 1 |

- `RunMap.build(run_id, term_count)` 在 `create` 时确定性生成整局地图（term_count × 8 个节点，不消费随机）。
- 节点 ID = `"<run_id>|t<学期>l<层>_<kind>"`，**按 ID 查询**（`RunState.find_node`）；同学期同层同类型唯一。
- 边 = 相邻层全连接（最多 2×2），只指向同学期、更高层；`next_ids` 保持模板顺序（普通在前、精英在后）。
- **可达性**：`RunState.reachable_node_ids()` = 局未结束、无待完成学期结算时，
  未进入任何节点→本学期第 1 层；当前节点已完成→它的 `next_ids`；当前节点 active→空数组。
  `enter_node` 只接受可达节点，因此**只能前进、不能回退、不能跳层、不能重进已完成节点**。
- 节点状态机：`pending → active → completed`。进入即 active；`completed` 之后不再可达。
- 事件节点在**没有任何合法事件**时按 §10.2 回退为普通战斗（`kind` 改为 normal，`node_id` 保留模板标识，
  并发 `event_fallback` 事件）。
- 战斗节点：`enter_node` 只负责抽遭遇（map 流）并返回 `battle_input`；**节点完成必须由 settle_battle + 奖励处理 + leave_node 走完**。
- 非战斗节点 `leave_node` 前置：商店随时可走；事件必须已选选项（「离开，无变化」也是选项）；休息必须先 `take_rest`；
  战斗节点必须已结算且 `pending_reward.is_complete()`。
- 第 6 层首领节点完成后进入**学期结算**：恢复 `max_vitality × term_heal_percent%`（向下取整，直接写回），
  再建立步骤：`direction_reward`（白/蓝卡三选一，可跳过；第 5 学期开始前追加不可跳过的 `career_track`）。
  步骤全部完成后 `term += 1`、清空 node_path，本学期第 1 层重新可达。
- 最终学期（`term >= term_count`）首领胜利：不发奖励与生活费，直接生成 `run_summary(won)` 并等待 `choose_ending`。

## 5. 随机流归属（关键不变量）

| 流 | 谁推进 | 何时推进 |
|---|---|---|
| map | RunService | 进入战斗/事件节点抽遭遇或事件定义（**候选池只有 1 个时不推进**，保持确定性） |
| reward | RunService | 战斗奖励候选生成、商店库存生成、事件随机候选冻结、学期方向奖励候选 |
| event | RunService | 保留给事件内部随机（当前内容未使用；事件候选走 reward 流） |
| battle | **BattleEngine** | RunService 任何路径都不得推进；`settle_battle` 只回传快照 |

`battle_input.rng_state` 与 `RunStep.rng_states` 都是完整快照；会话层统一合并进 `SessionState.random_snapshot`。

## 6. 幂等键（重复提交必须被拒）

| 操作 | 幂等键 | 重复提交返回 |
|---|---|---|
| settle_battle | `battle_id`（= 节点 ID），存 `RunState.settled_battle_ids` | `ALREADY_RESOLVED` |
| claim_reward | `(offer_id, item_id)`，`RewardItem.status` = pending/claimed | `ALREADY_RESOLVED` |
| skip_reward | `(offer_id, item_id)`，status = skipped | `ALREADY_RESOLVED` |
| buy_item | `stock_id`，`StockItem.sold` | `ALREADY_RESOLVED` |
| remove_card | `ShopState.removal_count`（每店上限） | `LIMIT_REACHED` |
| choose_event | `event_instance_id`，`EventState.resolved_option_id` | `ALREADY_RESOLVED` |
| take_rest | 节点 ID，`node.context.used` | `ALREADY_RESOLVED` |
| enter_node | 节点 ID + status | `ALREADY_RESOLVED` / `INVALID_TARGET` |
| choose_term_option | `step_id`，step.status | `ALREADY_RESOLVED` |
| choose_ending | `run_summary.ending_id` | `ALREADY_RESOLVED` |
| abandon_run | `outcome` | `WRONG_PHASE` |
| Profile 合并 | `RunSummary.run_id`（存档层三步提交） | 不重复记录 |

## 7. 数值来源（与 data/definitions/rulesets.json 一致）

| 行为 | rulesets 键 | 当前值 |
|---|---|---|
| 初始精力/钱 | run.starting_vitality / starting_money（难度覆盖 `difficulty_overrides`） | 72 / 60（relaxed 84，hard 72） |
| 起始牌组 | run.common_starter_cards + 人物 starter_cards；校验 run.starter_deck_size | 10 + 2 = 12 |
| 牌组下限 | run.minimum_deck_size | 5 |
| 学期数/每学期节点 | run.term_count / nodes_per_term；与地图模板校验一致 | 8 / 6 |
| 学期恢复 | run.term_heal_percent（向下取整） | 20% |
| 休息恢复 | run.rest_heal_percent（向下取整） | 25% |
| 普通战生活费 | rewards.normal_money_by_term[term-1] | 15/15/20/20/25/25/30/30 |
| 精英加成 / 非最终首领 | rewards.elite_money_bonus / nonfinal_boss_money | +20 / 50 |
| 奖励候选数量 | rewards.candidate_count | 3（不足时显示实际数量） |
| 卡品质权重 | rewards.card_rarity_weights.{normal,elite,boss,term} | 60/30/9/1、20/45/30/5、0/30/50/20、50/50/0/0 |
| 饰品品质权重 | rewards.relic_rarity_weights.{general,boss} | 50/35/13/2、20/40/35/5 |
| 饰品池耗尽 | rewards.empty_relic_pool_money | 30（转生活费） |
| 商店库存 | shop.card_stock / relic_stock / meal_stock | 白2蓝2紫1 / 白1蓝1 / 餐食1 |
| 商店价格 | shop.card_prices / relic_prices / meal_price | 35/55/85、80/120、25 |
| 餐食恢复 | shop.meal_heal | 12 |
| 删牌 | shop.removals_per_shop / first_removal_price / removal_price_increment | 1 / 60 / +20 |
| 升级上限 | run.max_card_upgrades | 1 |

规则要点：品质先按相对权重抽，**池为空的品质不参与并在剩余品质上重新归一化**；零权重品质不会被抽中；
奖励卡池排除 `basic` 标签；商店卡池只按品质与定价过滤（§10.1 只禁止金卡/金饰品）；
饰品池排除 `availability=starter`、已持有同名与 `rarity=null`。

## 8. 奖励 / 商店 / 事件 / 休息

- **战斗奖励**：`settle_battle(win)` 在同一次提交里写回精力、发生活费、生成 `RewardOffer`（候选冻结）。
  普通战 = 卡三选一；精英 = 卡三选一 + 随机饰品 1 件；非最终首领 = 卡三选一 + 饰品三选一。
  生活费与「饰品池耗尽折算」都是**直接收益**，记在 `offer.meta.money` 供界面展示，不作为待处理 item。
- **领取**：`claim_reward{offer_id, item_id, candidate_id?, replace_relic_id?}`。候选只有 1 个时可省略
  `candidate_id`；满饰品槽必须给 `replace_relic_id`（`LIMIT_REACHED`），同名饰品已持有返回 `ALREADY_RESOLVED`。
- **跳过**：`skip_reward` 只对 `item.skippable=true` 的项有效。
- **交易原子性**：`buy_item` / `remove_card` 走 `TransactionResolver.prepare → apply`：价格由服务现算（不采信 UI），
  全部校验通过才整体应用；**取消交易停在 UI，不发命令，因此不扣钱**；失败连随机快照都不提交。
- **事件**：进入节点时抽 1 个未见过的事件（map 流）并把 `seen_event_ids` 记为已见（离开也算）；
  带 `rarity` 的随机收益候选在进入时冻结（`EventState.frozen_candidates`），重开界面不重抽。
  `choose_event` 一次性收齐成本与全部收益目标后提交；**校验全部收益 op 通过才扣钱**。
- **休息**：`take_rest{node_id, option_id, card_instance_id?}`，`option_id ∈ heal / upgrade / remove_burden / train`；
  升级与训练要求 `upgrade_level < max_card_upgrades`；删负担要求卡定义 `tags` 含 `burden` 且牌组 > 下限。

### 事件定义 schema（内容侧按此写 `data/definitions/events.json`）

```json
{
  "id": "V01", "name_key": "event.v01.name", "terms": [1, 8], "once_per_run": true,
  "options": [
    {"option_id": "home", "label_key": "event.v01.home",
     "cost": {"money": 0, "vitality": 0},
     "effects": [{"op": "gain_relic", "rarity": "white", "fallback_money": 20}]},
    {"option_id": "leave", "label_key": "event.v01.leave", "effects": []}
  ]
}
```

- `terms`（或 `allowed_terms`）写 `[lo, hi]`；缺省表示不限学期。
- 事件效果 op：`gain_money{amount}`、`heal{amount}`、`lose_vitality{amount}`、
  `gain_card{card_id}` 或 `gain_card{rarity, candidate_count?}`、`gain_relic{relic_id}` 或
  `gain_relic{rarity, count?}`、`upgrade_card`、`remove_card`、`career{track, amount}`。
  未知 op → `CONTENT_INVALID`。
- 需要目标的 op 由 `choose_event.selection_ids[]` 提供目标实例 ID；满饰品槽用 `replace_relic_id`。
- **候选池为空 / 已持有同名饰品**时必须给出 `fallback_money`（如 §10.2 的「否则 20 生活费」），
  否则返回 `CONTENT_INVALID`——RunService 不发明数值。
- 每个事件都必须包含「离开，无变化」选项（`effects: []`）；支付后精力必须 ≥ 1。

## 9. 视图与页面路由（`make_view`）

顶层：`run_id / character_id / ruleset_id / difficulty / manifest_id / term / term_count /
nodes_per_term / money / vitality / max_vitality / career{} / career_direction / relic_slots /
cards[] / relics[] / deck_size / removals_used / current_node_id / node_path[] /
reachable_node_ids[] / nodes[]（本学期 8 个）/ node / battle / pending_reward / shop / event /
rest / settlement / outcome / run_summary / eligible_endings[] / screen`。

`screen` 由 RunService 给出，界面直接按它切页：
`ending`（通关待选结局）→ `summary`（局结束）→ `term`（学期结算）→ `reward`（待处理奖励）→
`battle` / `shop` / `event` / `rest`（当前 active 节点）→ `map`。

节点视图关键字段：`node = {node_id, term, layer, kind, status, next_ids, encounter_id, event_definition_id}`；
`battle = {battle_id, encounter_id, settled}`；`reward` 每项 `{item_id, kind, candidates, status, chosen_id, skippable}`；
`shop.removal = {available, used, max, price, money, minimum_deck_size, deck_size}`；
`rest.options[] = {option_id, enabled, blocking[], needs_card}`；`rest.heal_amount` 已按最大精力算好；
`event.options[] = {option_id, label_key, cost, effects, candidates, enabled, blocking[]}`。

## 10. 错误码与行为

| 场景 | 返回 | 是否有副作用 |
|---|---|---|
| 未知人物/清单不含定义/无合法遭遇/未知事件 op/事件无 fallback | `CONTENT_INVALID` | 无（在扣钱与发牌之前返回） |
| 未知难度、非法 seed、非法结局值、缺 payload、未知操作 | `INVALID_ARGUMENT` | 无 |
| 跳过层、未知节点、目标不存在、候选不在冻结列表 | `INVALID_TARGET` | 无 |
| 钱/精力不足、满槽未给替换对象、牌组低于下限 | `INSUFFICIENT_RESOURCE` / `LIMIT_REACHED` | 无 |
| 重复结算/领奖/购买/休息/事件/步骤/结局、重进已完成节点 | `ALREADY_RESOLVED` | 无 |
| 战斗未结算时做任何局流程写操作、结算期间进节点、已离开商店再交易 | `WRONG_PHASE` | 无 |
| 奖励未处理完就离开节点 | `CHOICE_PENDING` | 无 |
| 随机快照算法版本不符 | `VERSION_MISMATCH` | 无 |

闸门规则：`outcome != ""` 时只接受 `choose_ending`；`active_battle_id != ""` 时拒绝全部写操作；
`pending_reward` 未完成时只接受领取/跳过；`settlement` 未完成时只接受 `choose_term_option`。

## 11. 与存档层的交界（RunCodec 已就位，待存档层两行委派）

`src/run/run_codec.gd`（`RunCodec`）负责本模块全部状态的编解码：
`RunCodec.encode_run(run) -> Dictionary` / `RunCodec.decode_run(data) -> RunState`，
内部覆盖节点上下文里的 `ShopState` / `EventState`、`RewardOffer`、`TermSettlement`、`RunSummary`
以及本文 §3 列出的全部新增字段。`decode_run` 会重建全部实例并按存档值覆盖实例 ID，
`next_instance_seq` 最后恢复（重建 cards/relics 会临时递增它）。
`tests/suites/test_run_service.gd` 的「RunCodec · 存读档往返」用 **JSON 字符串往返** 验证无损。

存档层只需要两行委派：

```gdscript
static func encode_run(run) -> Dictionary:
    return RunCodec.encode_run(run)

static func decode_run(data: Dictionary):
    return RunCodec.decode_run(data)
```

**实测结论（2026-10 更正）**：`src/storage/snapshot_codec.gd` 目前并没有走上面那两行委派，
而是自己搬运 `RunState`（显式字段 + 逐个子实体重建：RunCard / OwnedRelic / RunNodeState /
RewardOffer / EventState / TermSettlement / RunSummary）。这**不减损完整性**——verifier 用真实
RunService 局做了对照实验：「存读档 → 继续同一学期」与「不存档」的控制组逐字段一致，
含 map / reward / event / battle 四条随机流。因此本文早先「委派前会丢地图与奖励进度」的说法
**已作废**（§9「不自动删未知内容」的约束仍然有效，`decode_run` 对未知键是保留而不是丢弃）。

`RunCodec` 仍是 `src/run` 侧的权威编解码（直接使用与单元测试都走它）。将来若把存档层改成
两行委派，必须保留上面那条对照用例：它现在挂在审查入口
`tests/suites/audits/audit_storage_run.gd` 的「§11 真实会话」节（刻意不入主套件基线）。
## 12. 已知内容缺口（不阻塞本模块）

- `data/manifests/mvp.json` 尚未启用首领 B01，因此**闭环验收使用 `battle_mvp` 清单**（含 N01 + B01）；
  mvp 清单下首领节点进入时按规则返回 `CONTENT_INVALID`（有专门用例覆盖），补齐内容（t6）后即可闭环。
- 精英遭遇（kind=elite）与事件定义（`events.json`）尚未落地：精英节点按「空池回归一化」走普通遭遇，
  事件节点按 §10.2 回退普通战斗；两者都有用例覆盖回退路径。
- `第 5 学期开始前的履历方向步骤`（`career_track`）已实现，但缺少 8 学期长跑的用例（当前只跑通第 1 学期）。

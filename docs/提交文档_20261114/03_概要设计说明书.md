# 《交大四年：DDL战争》概要设计说明书

文档编号：SD-01　版本：1.0　日期：2026-11-14

提交基线：DOC-20261114-1　适用模式：campus_four_year / 人物规则v3.1

## 1. 设计目标与约束

核心设计承接01冻结需求，覆盖四角色卡牌战斗、逐年地图与节点经济、稳定保存/恢复和只读界面。采用现有Godot/GDScript工程、本地JSON内容与聚合JSON存档；不引入SQL、联网后台或新的运行时架构。本文记录当前工程边界和必须保持的不变量，未实现项仍按需求书Q清单管理。

## 2. 系统上下文与分层

玩家/键鼠 → UI展示与草稿 → GameSession → RunService或BattleEngine；领域服务读取ContentDB并使用RandomSource。GameSession通过SnapshotCodec协调RunCodec/BattleCodec，再交SaveStore写文件；ProfileMerge按run_id合并总结。测试房间通过同一会话外观进入独立TestRoomService与TestStore。

| 层/模块 | 责任 | 输入与输出 |
|---|---|---|
| UI / GameShell | 展示副本、构造草稿/命令、消费事件；新视觉仍依文字需求和资源门槛 | 键鼠→ActionDraft/CommandContext/GameAction；SessionView→可见页面 |
| GameSession | 唯一正式命令入口；路由、revision、状态/RNG共同发布、存储状态 | StartRunRequest/命令→ActionResult/GameResult |
| ContentDB | 整包schema/ID/引用/op校验，发布只读定义索引 | manifest/definitions→ContentInfo/只读定义 |
| BattleEngine及规则模块 | 有效面、费用、目标、队列/待选、人物/单位/章节/阶段 | BattleState＋动作＋RNG→BattleStep |
| RunService / CampaignService | 地图/年度、节点/奖励/交易、战斗输入/结果、总结 | RunState＋动作＋RNG→RunStep |
| RandomSource | map/reward/event/battle独立版本流，完整导出恢复 | 主种子/快照→受控随机与新快照 |
| Codecs / SaveStore | 领域字段映射与外壳分离；临时写/校验/备份/替换 | 稳定SessionState→快照→SaveReceipt或诊断 |
| ProfileMerge | 终局跨文件幂等 | terminal_summary/run_id→去重Profile与提交状态 |
| TestRoomService / TestStore | 测试覆盖、编辑事务、历史/检查点、独立文件 | test上下文/patch→测试视图/结果；不触及正式档 |

只展示四年新局，四人12张起手；ContentDB整包校验，所有永久来源共用角色资格。

### SD-05 存储与总结

### SD-06 随机与界面

四流确定性，UI只读和事实事件，设置独立保存，资源按台账分阶段核对。

测试上下文隔离；性能、自然路径、导出需独立证据。

## 4. 主要流程与状态边界

正式局：菜单→新局/继续→地图→当前节点→完成条件→地图。战斗结束由会话调用RunService结算，生成普通奖励或年度offer；年度奖励与方向/去向均解决后才生成下一年。大四大奖励解决进入总结；失败/放弃也形成一次总结。

战斗：准备→行动→合作→弃牌→任务→完整轮末。每条动作必须结束于稳定状态或唯一待选；待选为仅驻内存的续算工作区。页面切换和动画只反映已发生结果，不决定战斗结算或推进RNG。

持久化与领域成功独立：规则可已成功而写盘失败。UI应分别报告业务接受、是否稳定、局保存、Profile合并与清标记，重试只处理缺失写盘，不重执行业务。

## 5. 数据设计概要

| 对象 | 所有者与职责 | 关键不变量 |
|---|---|---|
| ContentInfo/定义 | ContentDB；版本、启用集合、内容hash | 只读、ID唯一、引用闭包、无任意字符串执行 |
| SessionState | GameSession；run/battle/RNG/revision/pending/summary | 唯一可变正式会话；状态与RNG共同发布 |
| RunState | RunService；永久牌、精力、经济、节点、campaign | 实例独立；年度输入与已公开候选冻结 |
| BattleState | BattleEngine；牌区、资源、任务/伙伴/场景及v3状态 | 主/副实例ID分离，阶段与限次不被换区刷新 |
| campaign | CampaignService；version/map_version/root_seed/years/summaries | 新局仅1年；旧图精确恢复，年度生成不依赖其他流调用次数 |
| Profile/Settings | 独立文件；长期去重/解锁与设置 | run_id幂等；音量字号不改局状态或随机 |
| 测试状态 | TestRoomService；覆盖层、branch、检查点 | 独立test上下文与文件，不并入正式Profile |

## 6. 接口、错误与质量属性

正式接口按start_run/restart_run、get_view、preview_action、submit、save_current/save_and_exit、continue_run/restore_backup、get_setup_options/update_settings组织。CommandContext只携带run_id和expected_revision；业务payload按动作白名单验证。拒绝以ApiError的code/message_key/details诊断，重点区分STALE_STATE、CHOICE_PENDING、INSUFFICIENT_RESOURCE、CONTENT_INVALID、SAVE_CORRUPT、VERSION_MISMATCH与SAVE_IO_ERROR。

系统以四流重放和规范化快照保证可复现，以副本事务保证失败原子性，以冻结候选和业务ID保证重试幂等。性能预算与证据采用SRS-039；参考机、自然路径、正式资源与发布尚未达成完整验收，不在概要设计中宣称通过。

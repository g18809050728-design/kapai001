## 3. 已复现的问题与不足

P1：优先修复，会导致错误恢复、实验状态损坏或丢失，或破坏编辑时输入隔离。P2：功能不一致、验证可信度不足或常规使用受影响。P3：局部可用性不足。共 6 项 P1、16 项 P2、1 项 P3；没有发现或宣称 P0 级正式数据损坏。

### A01 · P1 · 检查点满 50 条后 ID 重复，点击最新项恢复到旧状态

- 复现：连续 55 次把专注设为 10…64，再恢复最后一条检查点。
- 实际：保留 50 条却只有 45 个唯一 ID；末尾反复为 `cp-51`。预期恢复专注 64，实际为 59。
- 原因：`TestRoomState.make_checkpoint()` 用当前列表长度编号，达到保留上限后不再增长；恢复取第一个同 ID 项。应使用独立单调序号/唯一 ID，并覆盖截断后的恢复。
- 位置：[test_room_state.gd:107](../src/test/test_room_state.gd#L107)、[test_room_service.gd:1039](../src/test/test_room_service.gd#L1039)。证据：core 的 `checkpoint-identifiers-stay-unique-after-capacity`、`last-checkpoint-restores-exact-state`。

### A02 · P1 · 待选选择“保留并截断”后无法继续战斗

- 复现：打出 R3-P01-16 产生待选，打开编辑器，修改专注，应用并选“保留并截断”，关闭编辑器，结束回合。
- 实际：顶层 `pending_choice=null`，但战斗 `phase=awaiting_choice`；结束回合报 `WRONG_PHASE`。回退策略没有此问题，取消策略保留待选、付款/卡牌/RNG。
- 原因：截断只清除了服务层待选，未恢复战斗阶段及清理引擎待选/结算上下文。需保证“截断”形成可继续的稳定边界。
- 位置：[test_room_service.gd:916](../src/test/test_room_service.gd#L916)。证据：edges 的 `truncate-subsequent-turn-usable`；ui-edges 的两次 `truncate leaves usable combat`；[清理前验证摘要](测试房间仓库清理_20261123.md)。

### A03 · P1 · 快照载入缺少完整结构校验

- 复现：在隔离 TestStore 保存 `core.battle.zones.hand` 含不存在实例引用的快照，或 `core={}`，再载入。
- 实际：两者均返回接受并激活实验。正常编辑的结构校验会拒绝缺失实例引用；载入绕过此保护。
- 影响：损坏文件可变成活动实验；后续页面/命令依赖完整 battle/RNG，存在异常风险。本次没有为了证明崩溃而继续强制运行空 battle。
- 位置：[test_room_service.gd:1285](../src/test/test_room_service.gd#L1285)。证据：core 的两个 `reject-…snapshot…`。外层 schema 不符、根类型错误、缺文件及 IO 失败有正确拒绝，不能笼统称“全部文件校验失效”。

### A04 · P1 · 定义和规则覆盖未按 schema/处理器校验

- 复现：新建卡牌效果 `op=AUDIT_UNREGISTERED_HANDLER`；把 `battle.focus_cap` 覆盖为 -50；另以 `count=1.5` 添加卡。
- 实际：全部接受。资源 `focus=1.5` 会拒绝，而卡牌数量被转成整数接受，字段校验不一致。
- 原因：覆盖层仅检查种类、命名空间、ID 及字段根白名单；缺类型、范围、效果处理器和引用闭包校验。应在事务发布前调用与内容包相当的验证，错误时保留原状态并定位路径。
- 位置：[test_overlay.gd:90](../src/test/test_overlay.gd#L90)、[test_overlay.gd:120](../src/test/test_overlay.gd#L120)、[test_room_service.gd:2552](../src/test/test_room_service.gd#L2552)。证据：core 的 `reject-unknown-effect-handler`/`reject-negative-rule-cap`；edges 的 `reject-fractional-card-count`。

### A05 · P2 · 不存在的卡牌 ID 也能加入手牌

- 复现：`add_card` 的 `definition_id=AUDIT.MISSING.CARD`、zone=hand。
- 实际：接受并生成实例；结构校验只检查定义 ID 非空，不确认它能被解析。章节分支反而正确检查空定义。
- 原因：`_definition()` 返回空字典，常规牌区分支却判断 `definition == null`。
- 位置：[test_room_service.gd:1757](../src/test/test_room_service.gd#L1757)、[test_room_service.gd:2779](../src/test/test_room_service.gd#L2779)。证据：edges 的 `reject-nonexistent-card-id`。

### A06 · P2 · 敌方任务可设置不存在的阶段

- 复现：`set_task_field` 将 phase_key 设为 `NO_SUCH_PHASE`。
- 实际：接受，并把不存在的阶段留在活动任务里。应验证任务定义的 phase 集合，或统一走专用阶段操作。
- 位置：[test_room_service.gd:2271](../src/test/test_room_service.gd#L2271)。证据：core 的 `reject-unknown-task-phase`。

### A07 · P2 · 预览表示“可应用”，提交却被开关限制拒绝

- 复现：所有开关默认关，将精力设为 0，先预览再应用。
- 实际：预览 `can_submit=true`；提交 `TEST_LIMIT_REACHED`，要求 `allow_zero_vitality`。
- 原因：预览没执行与应用相同的开关限制/待选策略处理。应共用一次完整校验并保持预览无副作用。
- 位置：[test_room_service.gd:819](../src/test/test_room_service.gd#L819)、[test_room_service.gd:853](../src/test/test_room_service.gd#L853)。证据：core 的 `preview-and-apply-agree-on-zero-vitality`。

### A08 · P2 · 当前起点重试可能重新接受旧请求

- 复现：保存新实验初始 context（branch 0 / revision 0），执行 current/same 重试，再用旧 context 提交编辑。
- 实际：旧请求仍接受。重试沿用 test_id，并重设 branch/revision 为 0，形成上下文重用。此前 revision 非 0 的普通旧请求拒绝正确。
- 建议：新尝试保持可区分身份，避免把单调上下文退回旧值。
- 位置：[test_room_service.gd:1134](../src/test/test_room_service.gd#L1134)。证据：core 的 `fresh-current-restart-invalidates-old-context`。

### A09 · P2 · 撤销再重做恢复状态，却丢失操作日志

- 复现：修改专注 → 撤销 → 重做。
- 实际：状态 hash 恢复正确，`journal.size()` 却为 0。
- 原因：历史栈仅存 journal_size；撤销先截断原日志，重做再从已截断日志取 slice，无法找回内容。影响实验取证、保存记录与未来重放。
- 位置：[test_room_service.gd:1074](../src/test/test_room_service.gd#L1074)。证据：core 的 `redo-preserves-operation-journal`。

### A10 · P2 · 实验记录忽略版本/hash，载入后丢弃日志

- 复现：保存记录，把 payload 的 `engine_version` 改为 `0.invalid`、`state_hash` 改成错误值，载入。
- 实际：接受，且载入后的 journal 为空。这里篡改的是记录 payload，外层文件 schema=99 仍会拒绝。
- 影响：记录目前只是恢复最终 core，不能作为经过校验的可重放证据。源码也没有真实重放执行/首差异定位流程。
- 位置：[test_room_service.gd:1332](../src/test/test_room_service.gd#L1332)。证据：core 的 `record-validates-engine-and-state-hash`。需明确“恢复记录”与“校验/重放”的区别。

### A11 · P2 · 数值锁定 API 返回成功但不生效（已知占位仍存在）

- 复现：专注设为 23，`set_player_lock focus=true`，实际结束回合。

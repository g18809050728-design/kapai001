# 《交大四年：DDL战争》架构设计基线

版本：v0.2｜日期：2026-10-14｜状态：目标架构；实施状态见[实施计划与验收基线](../实施计划与验收基线.md)

实施顺序和退出门槛以[实施计划与验收基线](../实施计划与验收基线.md)为准。模块调用契约见[接口文档](接口文档.md)。

内部职责见[初步架构设计 §10](初步架构设计.md)，实体与持久化结构见[数据库与实体关系设计](数据库与实体关系设计.md)。目标存储采用只读 JSON 内容库与本地聚合快照，ContentDB 负责索引和引用校验；此处是设计目标，不代表当前已有实现。

## 1. 目标与范围

采用 **Godot 4＋GDScript 的本地单体架构**，将战斗规则、局流程和界面表现分开。目标内容格式为 JSON，进度保存到本地文件；当前工作区没有工程文件，精确引擎版本和实际存储格式须在 G1 锁定。

最终切片目标是跑通一学期：选人物→地图→战斗/事件/商店/休息→考试首领→结算。当前先完成可无头验证的规则、内容、局流程和存档；AI 图片生成、UI 与剩余交付项安排在后续阶段。精确 MVP 内容和玩法数值须按 README 所列上游来源在实施计划 G0 核对并冻结；四份来源已纳入 docs/，精确范围见 baselines/g0.json。

必须满足三个要求：规则可以独立测试；动画不影响结果；退出后可以继续同一局。每项都对应[实施计划与验收基线](../实施计划与验收基线.md)中的验收 ID 和证据。来源、玩法范围与地图已融合；实现和运行数值仍须后续阶段验证。

## 2. 总体结构

```text
玩家操作
   ↓
UI：页面、卡面、目标选择、动画
   ↓ 操作请求                  ↑ 状态快照与事件
GameSession：协调当前局、战斗和页面切换
   ├── BattleEngine：战斗规则
   ├── RunService：地图、奖励、交易、成长
   └── SaveStore：保存与恢复
          
BattleEngine / RunService
   ├── ContentDB：只读内容定义
   └── RandomSource：可保存的随机状态
```

规则核心使用普通数据对象，不依赖Godot场景树、动画和音频。GameSession 是唯一可变会话状态的持有者和规则命令入口；UI 只提交命令草稿并展示返回视图/事件，不能持有 BattleState、RunState 或直接调用引擎写操作。

## 3. 模块职责

| 模块 | 负责 | 对外操作 |
|---|---|---|
| GameSession | 持有当前会话，协调流程与保存 | 新局、继续、提交操作、退出 |
| BattleEngine | 出牌、回合、状态、单位、场景、考试、胜负 | 开战、预览、出牌、确认选择、结束回合 |
| RunService | 地图、永久牌组、奖励、商店、事件、履历 | 进入节点、结算战斗、领取、购买、休息 |
| ContentDB | 加载并校验定义，筛选G0批准且由G2验证的生产内容 | 按ID查询、获取合法候选池 |
| RandomSource | 洗牌、掉落、事件和场景随机 | 抽取、导出/恢复随机状态 |
| SaveStore | 当前局、解锁和设置的文件读写 | 保存、读取、恢复备份 |
| UI | 页面、输入、提示与表现 | 渲染快照、发送操作请求 |

GameSession负责协调，不承包牌效和商店算法。初期在所属模块内用函数拆分；功能规模增长后再提取独立类。

## 4. 核心数据与归属

| 数据 | 主要字段 | 写入者 |
|---|---|---|
| ContentDef | 人物、卡牌、单位、场景、饰品、任务、事件定义 | ContentDB加载后只读 |
| RunState | 人物、难度、学期、节点、精力、钱、永久牌、饰品、履历、待领奖励 | RunService |
| BattleState | 回合、DDL、专注、精力、牌堆、状态、单位、任务阶段、场景、触发次数 | BattleEngine |
| Profile | 解锁、设置、教学记录、已结束局摘要 | GameSession调用存储更新 |

战斗期间精力以BattleState为准，RunState中的值仅为入场记录；战斗结束后一次性写回。抽弃牌不会修改永久牌组。BattleEngine 由 GameSession 调用，战斗 UI 不拥有引擎或可变 BattleState。

内容定义ID与运行实例ID分离：K01表示“写”的定义，同局多张K01各有实例ID。升级修改永久实例的升级等级；进入战斗时生成对应战斗实例，临时牌战后移除。

不同内容包共用已批准的数据格式，由启用清单筛选内容；每个清单发布前必须验证启用项及其传递引用均已包含。实际生产范围与引用闭包在 G0/G2 验证，不能根据本段推断内容已启用。

## 5. 核心流程

### 5.1 出牌

1. UI选择卡与必要目标，经GameSession向BattleEngine请求预览；预览不改变状态或随机序列。
2. 引擎先解析考试替代面，再检查目标、费用、资源、单位容量与限次。
3. 校验通过后支付并执行效果，按明确顺序处理触发、暂离、转阶段和胜负。
4. 返回更新后的状态、表现事件，以及可能需要的后续选择。
5. 效果队列完成或产生终局后，会话层发布规则稳定状态；待选续算可发布给当前会话以等待确认，但只驻内存且不可保存。`stable` 只表示规则队列已完成，不代表已写盘；自动保存策略决定是否立即持久化。

支付前的目标或换班选择可以取消。抽牌后弃牌等效果内选择必须先完成，不能取消整条已支付命令并继续其他规则操作；若进程在选择完成前中断，下次启动从最近一次成功写盘的稳定快照恢复。自动保存关闭，或自动保存失败后中断时，恢复点可能早于最近一次内存稳定提交。

操作带状态版本号，旧界面的重复请求拒绝执行。UI提交后锁定对应操作，防止连点重复支付。无效操作不改变资源或随机状态。

### 5.2 战斗回合

```text
准备 → 抽牌 → 玩家出牌 → 合作行动 → 弃牌
     → 敌方准备 → 敌方技能 → 敌方压力 → 轮末与DDL
     → 下一回合 / 胜利 / 失败
```

回合和胜负规则沿用游戏规则书固定编号。尤其保证：考试转换用于预览和实际执行的同一套逻辑；首领转阶段完成后才能判胜；最终任务完成立即结束；DDL超时不被精力救命效果抵消。

触发顺序显式写入规则代码，不依赖节点、字典或动画回调的遍历顺序。同窗按已确认 [RES-001] 的创建顺序、稳定 ID 和同源效果数组顺序；首轮按 [INI-001]，不得另立类别优先级。

### 5.3 局流程与交易

```text
选择人物 → 学期地图 → 节点处理 → 节点结算 → 学期地图
学期首领胜利 → 奖励与学期结算 → 下一学期
最终首领胜利 → 结局；战斗失败 → 本局总结
```

战斗结束返回结果，由RunService写回精力、生成奖励并推进节点。通过战斗ID和节点领取标记避免重复结算。

商店与事件先收集全部选择，再一次性校验并提交成本和收益。取消饰品替换不扣钱；奖励、库存和随机候选生成后保存，重新打开界面不重抽。

## 6. 内容与存档

### 内容配置

按人物、卡牌、单位、场景、饰品、状态、任务、事件分类保存JSON。卡牌至少包含ID、名称、类型、品质、费用、目标、效果、升级和耗尽标记。

常见效果用有限处理函数实现，如完成、压力、抽牌、放松、状态、召入单位、换场；复杂牌用专用函数组合，不先制作通用脚本语言或可视化编辑器。

加载时检查ID唯一、字段合法、引用存在、升级完整、MVP依赖齐全。JSON是实际运行来源；平衡调整同时更新统一设计文档。

### 保存与恢复

- 分别保存当前局、长期解锁和设置，存档目标字段包含格式版本、内容版本及随机状态。
- 当前局由SessionState统一保存RunState、可选BattleState、随机状态、唯一 terminal_summary 与 profile_merge_pending 标记以及 event_log；新局revision为0，后续只由会话层管理。结局先持久化待合并摘要，再按run_id幂等写入Profile，最后清除待合并标记；三步的部分成功状态按接口分别报告。
- 在规则稳定边界可保存；`autosave=true` 时稳定提交后立即尝试自动保存，关闭时只由显式保存或 save-and-exit 持久化。待选续算未完成时不保存半成品；保存失败保留会话内存结果并报告错误，异常退出恢复最近一次成功写盘的快照。
- 终局摘要只有在包含它的 current_run 快照成功写盘后才能合并到 Profile；自动保存关闭时，摘要合并随显式保存发生。
- 战斗存档包含牌堆、任务阶段、意图、触发次数和场景已预抽结果，不能只保存血量与牌组。
- 先写临时文件并校验，再替换正式档，保留上一份有效备份；损坏时可恢复备份。
- 读档检查版本兼容，不能静默删除未知卡牌或重置当前局。

随机源按地图、奖励、事件、战斗分开，保存各自状态。预览和取消选择不消费随机；同版本、相同存档与操作应得到相同结果。

## 9. 关键取舍与待验证项

| 决策 | 理由与代价 | 重评条件 |
|---|---|---|
| 本地单体、核心与UI分离 | 适合单机小团队；需额外维护状态与展示转换 | 明确增加多人或在线功能 |
| JSON＋有限效果函数 | 便于调数值和检查；复杂牌仍需要代码 | 大量牌反复需要相同新增组合能力 |
| 稳定边界快照 | 恢复简单可靠；未完成选择不能保存半张牌 | 确实需要保存任意中间状态 |
| 同步规则、异步动画 | 结果稳定易测；长结算需要性能检查 | 实测单次结算影响交互 |

原型优先验证专注经济、单位续航、考试转化效率和单学期时长。屏障细分、同窗触发排序等局部细节必须在相关规则进入 G0 冻结或对应战斗阶段前变成明确规则用例；不能留给实现时临场决定。


## 10. 内部类职责与实体行为

### 10.1 分层与依赖

采用轻量分层单体。Godot节点只承载应用生命周期和界面，规则与数据类使用RefCounted。复杂度集中在明确的战斗与局流程边界内。

```text
表现层：页面、组件
    ↓ GameAction / ↑ View
应用层：GameSession
    ↓
领域层：BattleEngine、RunService、状态与内容定义
    ↓ 只读内容、工作副本中的随机源
基础设施：ContentDB、RandomSource、SaveStore、SnapshotCodec
```

依赖通过构造参数传入，GameSession作为唯一会话入口。领域层不引用UI、磁盘、信号或全局Autoload状态。公共接口沿用接口文档；本篇规定内部职责和实体行为，不另设一套API。

#### 类关系概览

```text
GameSession
 ├─ owns SessionState 与本次会话 revision
 ├─ calls BattleEngine → CardResolver、EffectResolver
 ├─ calls RunService → RewardGenerator、TransactionResolver
 ├─ reads ContentDB
 ├─ calls SnapshotCodec 协调领域 Codec，再调用 SaveStore 文件 IO
 └─ builds SessionView

SessionState
 ├─ RunState
 ├─ BattleState（0或1）
 └─ RandomSnapshot
```

辅助规则类可先作为所属模块内函数实现；达到独立测试和多人协作需求时再独立成文件，不建立空接口、通用仓储基类或每张牌一个子类。

### 10.2 应用层

#### GameSession：会话协调器（Node）

**持有**：ContentDB、BattleEngine、RunService、SaveStore、SessionState、ProfileState、SettingsState、is_submitting；持久化进度以 SaveStore 最近成功写盘的快照为准，不另造“内存稳定快照”等同于磁盘的状态。

**公开方法**：start_run、continue_run、get_view、preview_action、submit、save_current、save_and_exit、get_profile、update_settings、inspect_saves、get_setup_options、restore_backup，参数与返回值严格沿用[接口文档第2节](接口文档.md)。

| 内部方法（伪签名） | 职责 |
|---|---|
| `_validate_context(context: CommandContext) -> ApiError?` | 检查run_id、revision、进行中提交与阶段 |
| `_make_working_state() -> SessionState` | 深拷贝可变状态；内容定义只读共享 |
| `_dispatch(work: SessionState, action: GameAction) -> Result<SessionState>` | 路由战斗或局操作，合并结果与随机状态 |
| `_finalize_battle(work: SessionState, outcome: BattleOutcome) -> Result<SessionState>` | 调用settle_battle，写回精力与奖励，统一提交 |
| `_publish(work: SessionState, events: Array<RuleEvent>) -> ActionResult` | 校验后发布；新局创建为revision 0，后续每个改变已发布会话状态的接受命令加1，生成View和信号 |
| `_persist_if_enabled() -> Result<SessionSaveResult>` | 规则稳定且自动保存开启时落盘；分别报告当前局写盘、Profile合并和待处理标记清理状态，失败不回滚已完成玩法 |
| `_apply_pending_summary() -> Result<ProfileCommitStatus>` | 仅在 current_run 含摘要且成功写盘后，幂等合并到 Profile，并报告标记清理结果 |

提交中再次进入submit返回WRONG_PHASE并说明busy；正常UI同时只发一个规则请求。已进入效果内选择的事务只接受confirm_choice。新局检查内存和磁盘中是否有未结束局，避免刚启动时直接覆盖存档。

**工作副本**：创建效果内待选时，会话发布带有续算游标的非稳定工作区，只向当前进程提供只读视图，且只接受对应的`confirm_choice`；该工作区不写盘。每条确认命令从最近已发布的工作区及随机快照复制后执行；仍有后续选择时再发布工作区，队列完成后一次形成规则稳定状态。每条被接受并改变状态的创建/确认命令各递增一次revision；非法确认或内部错误只丢弃本条尝试副本，不回退此前已发布的工作区。规则稳定不等于已持久化：自动保存关闭时只有显式保存写盘，写盘失败时内存状态保留且可重试保存。新进程只从最近一次成功写盘的快照恢复，不复用旧UI请求。

#### SessionState：会话聚合（RefCounted）

字段：run、battle可空、random_snapshot、revision、terminal_summary可空、profile_merge_pending:bool、event_log；run_id取自run。RunSummary由RunStep finalize 后只由 terminal_summary 持有并作为终局视图来源；合并清理只清 bool，摘要继续保存。只有GameSession发布该聚合。BattleState和RunState不各自累加revision。

方法：`copy_for_write() -> SessionState`、`has_pending_resolution() -> bool`、`is_rule_stable() -> bool`、`validate(catalog: ContentDB) -> Array<ApiError>`。`is_rule_stable()` 只判断无效果续算，不声称状态已写入磁盘。

### 10.3 战斗领域

#### BattleEngine：战斗聚合服务

公开方法的唯一签名见[战斗模块契约 §1](战斗模块契约.md)。apply显式接收SessionState中的完整四流随机快照，只推进 battle。

| 内部方法 | 输入→输出 | 约束 |
|---|---|---|
| `_play_card` | state、PlayCardPayload→BattleStep | 先有效卡面再校验，结算牌进入resolving区 |
| `_confirm_choice` | state、ChoicePayload→BattleStep | choice_id匹配，接续ResolutionState游标 |
| `_set_ally_target` | state、unit_id、task_id→BattleStep | 只更新合法协作目标 |
| `_end_turn` | state、保留卡ID→BattleStep | 验证保留后驱动合作、弃牌和敌方回合 |
| `_advance_until_input` | context: BattleContext→Result | 推进到玩家行动、待选择或终局 |
| `_check_outcome` | context→BattleOutcome? | 救命与强制阶段处理完成后判定 |

BattleContext仅在一次执行中使用：工作状态、只读内容、有效规则、工作随机源、事件列表、效果队列。执行器不得持有另一份跨调用可变战斗；待选游标全部放ResolutionState。

#### CardResolver：出牌解析

| 方法 | 返回 | 用途 |
|---|---|---|
| `resolve_face(state, card_id) -> Result<EffectiveCard>` | 基础/升级/考试后卡面 | UI和执行共同读取 |
| `calculate_cost(state, face) -> CostQuote` | 费用、精力代价、优惠来源 | 不消费优惠 |
| `validate_play(state, payload) -> Result<PlayPlan>` | 目标、费用和效果快照 | 不能扣资源或抽随机 |

PlayPlan只在当前revision和当前命令中有效，不能作为可跨回合重用的凭证；CostQuote不包含可变状态引用。

#### EffectResolver：有限效果与触发执行

| 方法 | 返回 | 用途 |
|---|---|---|
| `execute(effect: EffectSpec, context) -> Result<EffectStep>` | 事件、后续效果或待选项 | 注册的op分派到具体处理函数 |
| `collect_triggers(event, context) -> Array<EffectSpec>` | 稳定排序后的触发 | 次数写在BattleState |
| `resume(choice, resolution, context) -> Result<EffectStep>` | 接续效果 | 校验数量与候选 |

EffectSpec JSON 为平铺的 {op, ...该 op 字段}，不使用 params 包装或额外 key；内部对象类型由 G1 实现，字段只按内容契约 §8。以有限注册函数处理完成、压力、抽弃、状态、恢复、召入、换场、保留等；未知op在内容加载时拒绝。需要新增特殊处理器时附牌例，不把任意字符串当代码执行。

#### 战斗实体行为

| 类 | 关键字段 | 领域方法（仅引擎内部调用） |
|---|---|---|
| BattleState | id、phase、round、ddl、player、cards、zones、units、tasks、scene、statuses、counters、resolution、next_creation_order、source_registry | `move_card(id, from, to)`；`get_entity(id)`；`is_stable()`；`validate()` |
| CombatantState | entity_id、max_vitality、vitality、relax | `gain_relax(amount)`；`receive_pressure(amount)`；`heal(amount)` |
| PlayerBattleState | CombatantState组合、focus | `pay_focus(amount)`；`gain_focus(amount, cap)` |
| UnitState | CombatantState组合、definition_id、cooperation、entered_order、actions_taken、target_id | `can_act(round)`；`mark_acted(round)` |
| TaskState | definition_id、phase_key、work_remaining、work_max、shield、intent_cursor、entered_order | `apply_completion(amount)`；`advance_intent()` |
| BattleCard | instance_id、definition_id、origin_card_id可空、upgrade_level、temporary_modifiers | `clear_expired_modifiers(timing)` |
| StatusState | instance_id、definition_id、holder_id、source、stacks、expiry、creation_order | `add_stacks(amount, cap)`；`consume(amount)` |
| SceneState | definition_id、instance_id、established_round、预抽结果 | 只记录数据；替换与触发由引擎处理 |
| ResolutionState | 原始动作、效果游标、冻结目标、待选项、队列 | 只存续算所需数据，不存Callable或Node |

压力/恢复方法只实现局部数值变化并返回变化量，救命、护卫、加值和阶段转换由引擎统一处理，不能在实体setter中隐藏触发。StatusState的source是不可变来源描述，不要求已离场来源仍存在。

玩家/友方有精力，任务有未完成量；不强行继承同一个“血条单位”基类，避免任务误用治疗和主角救命逻辑。

### 10.4 局流程领域

#### RunService

公开方法的唯一签名见[局流程契约 §1](局流程契约.md)。create从种子初始化，其余写操作显式接收会话随机快照。

| 内部方法 | 返回 | 负责 |
|---|---|---|
| `_enter_node(state, node_id)` | RunStep | 可达性、节点锁定、建立BattleInput或局外上下文 |
| `_claim_reward(state, payload)` | RunStep | 候选、领取标记、饰品替换 |
| `_take_rest(state, payload)` | RunStep | 恢复、升级、训练或删负担 |
| `_advance_term(state, payload)` | RunStep | 学期步骤标记、履历、方向奖励 |
| `_finish_run(state, ending_id)` | RunStep | 条件检查、生成待合并摘要 |

#### RewardGenerator与TransactionResolver

| 类/方法 | 职责 |
|---|---|
| `RewardGenerator.generate(source, run, rng) -> Result<RewardOffer>` | 用过滤后合法池抽候选，结果存入局状态 |
| `RewardGenerator.generate_shop(node, run, rng) -> Result<ShopState>` | 生成并冻结库存与来源价格 |
| `TransactionResolver.prepare(run, action) -> Result<TransactionPlan>` | 收齐成本、删除/升级对象、替换与收益，验证余额和下限 |
| `TransactionResolver.apply(run, plan) -> Result<RunState>` | 当前命令工作副本上一次应用，失败不发布 |

TransactionPlan包含基于当前状态算出的价格，UI不能传入；不允许跨revision缓存后直接apply。免费事件及休息升级也复用目标检查。

### 10.5 内容、存储与表现类

#### ContentDB

拥有只读 definitions_by_kind[kind][id] 和启用集合；公共目标签名在本节唯一维护：

| 方法 | 参数 → 返回 | 约束 |
|---|---|---|
| load | (manifest_id:String) → Result<ContentInfo> | 解析/合并/完整校验后一次发布；失败保留旧索引与hash |
| get_definition | (kind:String,id:String) → Result<只读定义> | 只查询启用内容，缺失返回CONTENT_INVALID，不返回可写共享对象 |
| get_candidates | (query:CandidateQuery) → Array<String> | 稳定ID升序、不随机；合法查询无候选返回[] |

CandidateQuery={kind,rarity可选,tags_all可选,exclude_ids可选,terms可选,availability可选}；未知键拒绝；kind是内容类型，terms为单个待匹配学期int（不同于定义中的集合），筛选条件AND。rarity=null用于显式筛选无品质；省略表示不过滤品质，业务奖池仍须按规则排除基础/特殊/初始饰品。排除同名、是否可获取由调用方提供条件，不在查询中抽取随机。

内部：`_parse_files()`、`_validate_definitions()`、`_validate_references()`、`_apply_manifest()`、`_build_indexes()`。全部通过后才发布新ContentInfo。类型化定义包含CardDef、CharacterDef、UnitDef、SceneDef、RelicDef、StatusDef、TaskDef、EncounterDef、EventDef、RulesetDef；字段与关系见数据库文档。

#### RandomSource

公共目标签名：draw_int(stream:String,min:int,max:int) → Result<int>（闭区间），shuffle(stream:String,ids:Array<String>) → Result<Array<String>>（返回副本），export_state() → RandomSnapshot，restore_state(snapshot:RandomSnapshot) → Result<bool>。RandomSnapshot={algorithm_version,streams:{map:{seed,state},reward:{seed,state},event:{seed,state},battle:{seed,state}}；seed/state为64位十进制字符串，具体算法及版本在G1锁定。恢复必须四流齐全，非法快照失败且保留原状态；查询导出不推进随机，min=max及长度≤1的抽取/洗牌不推进。stream必须已注册，非法参数零副作用。

工作执行创建独立RandomSource并restore输入快照，成功随SessionState发布，失败丢弃；注入的是随机源工厂/构造能力，不是可被失败命令污染的共享全局状态。

#### SnapshotCodec与SaveStore

| 类 | 责任/签名位置 |
|---|---|
| RunCodec / BattleCodec | 独占所属领域字段映射，见存储契约§11.1 |
| SnapshotCodec | 协调领域Codec及版本/兼容/迁移；精确签名唯一见[存储§11.1](数据库与实体关系设计.md) |
| SaveStore | 限定槽位文件IO/备份/checksum；精确签名唯一见[存储§11.2](数据库与实体关系设计.md) |

SaveStore不导入战斗UI或运行牌效；不为每个实体创建文件仓储。Profile和Settings编码按相应槽位类型处理。

#### 表现类

- AppRoot（Node）：装配依赖、接入GameSession信号、切换页面。
- BattleScreen/MapScreen等（Control）：`render(view)`、`build_action()`，不直接读取SaveStore。
- CardView/UnitView/TaskView（Control）：`bind(view)`、`set_selected(bool)`，只展示数据。
- 动画队列：`play(events)`、`skip_to_end()`；两条路径只能改变表现，不能调用伤害或领奖接口。

View构建先保留为make_view内部函数；需要复用复杂格式化时再提取ViewBuilder。接口中的`Result<T>`是设计记法，GDScript实现使用明确数据类或统一Result容器，不假定语言支持自定义泛型。

### 10.6 两个关键执行场景

**出牌**：GameSession校验版本→工作副本→CardResolver生成PlayPlan→EffectResolver执行→BattleEngine检查终局→必要时RunService结算→每条接受的会话命令提交一次 revision→待选时只保留内存续算，规则稳定后按 autosave 策略写盘→UI消费事件。

**购买**：UI提交库存ID和替换对象→TransactionResolver读取真实价格、检查余额和容量→在工作副本扣款并发放，库存标记售出→整体发布→按 autosave 策略持久化。取消只停留在UI预选，无业务调用。

### 10.7 实施与验收

实施必须先完成 G0 基线核对，再按根目录[实施计划](../实施计划与验收基线.md)的 G1–G8 顺序进行；SnapshotCodec 属于 G5，图片和 UI 属于 G6/G7。每个文件只在所属阶段实际实现其行为时创建，本文不是已完成类库。

类边界验收：引擎可headless运行；UI不持有可写状态；预览不改随机；副本深拷贝嵌套容器；卡区域唯一；异常不提交半条事务；终局和奖励不会因重复回调再次生效。存档/Profile 提交由 GameSession 协调器执行，SaveStore 不解码规则、不迁移、不补内容元数据；SnapshotCodec 负责兼容协调。

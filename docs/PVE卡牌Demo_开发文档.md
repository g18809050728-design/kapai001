# 一、项目概览

单人 PVE 回合制卡牌战斗 Demo。玩家扮演进入遗迹的冒险者，在「遗迹入口」与练习魔像战斗，击败魔像即完成 Demo。

- **引擎**：Godot 4.7.2（GDScript），标准非 mono 构建
- **设计分辨率**：1600 × 900，窗口默认 1280 × 720
- **启动**：直接进入战斗，无主菜单

```powershell
$godot = "D:\Tools\Godot_v4.7.2-stable_win64.exe"
& $godot --path D:\Code\card
```

## 2.4 开发过程中修掉的问题

留档的原因：这些都是**测试策略的教训**，后续升级要继续防。

| # | 问题 | 根因 | 修法 |
|---|---|---|---|
| 1 | 卡牌实例同时存在于结算区与场上区域，违反区域互斥 | `_summon` / `_play_scene` 用了 `set_zone()` 而非 `_move_instance()` | 统一走 `_move_instance()` |
| 2 | 随从击杀魔像后敌方阶段仍然执行 | `confirm_end_turn` 未在终局后中断 | 加入 `if not state.battle_over()` 守卫 |
| 3 | **无法出牌**：点一下选中、同一下又取消 | `_refresh_hand()` 销毁了正在处理该次点击的卡牌，`accept_event()` 失效，事件冒泡到 `_unhandled_input` 被当成「点击空白处」 | 选中态改为就地更新（`_update_selection_visuals()`），不重建节点 |
| 4 | 点空白 / 右键取消选择从不生效（被 #3 掩盖） | 根 `Control` 默认 `mouse_filter = STOP`，吃掉空白处鼠标事件 | 根节点设 `IGNORE`，另加位于最底层的空白处 catcher |
| 5 | 测试偶发失败 | 断言用「手牌数量 -1」，但抽到「战术整理」时会抽 2 张 | 改为判断「该实例是否已离开手牌」，与抽牌无关 |

> **教训**：前 2 个是规则层 bug，被逐条断言抓到；后 3 个中的 #3、#4 直接调用处理函数的测试**抓不到**，必须用 `push_input` 走真实事件路由。后续升级任何新的交互都要在 `ui_input.gd` 里补一条真实输入用例。

# 三、架构与约定

## 3.1 分层

```
src/core/   ← 规则层：纯 GDScript，不 extends Node、不碰任何 UI
              battle_types / card_db / enemy_db / battle_state / battle_engine
src/ui/     ← 界面层：只播放事件，绝不计算伤害
              battle_scene / card_view / minion_view / palette
```

**规则层是唯一权威**：伤害、能量、抽牌只在这里算一次。可用固定随机种子完整复现一场战斗。

## 3.2 事件链

每个规则入口返回**有序事件数组**，界面照着播放即可。

```
规则入口（play_card / confirm_end_turn / enemy_phase …）
        ↓ 改状态 + 按发生顺序追加事件
   有序事件数组  ← 唯一的一条「发生了什么」的记录
        ↓
界面只负责播放
```

跑 `tests/event_trace.gd` 可看到完整示例。一条典型链（打出一张攻击牌）：

```
card_moved         斩击　手牌 → 结算区          ← §6.3 普通牌先进结算区
card_played        打出「斩击」
attack_card_used   本回合已成功使用攻击牌 1 张
energy_changed     delta=+1 → 2（来源 卡牌效果） ← 效果声明「先回能，后伤害」
card_gained_energy 「斩击」作为卡牌效果回能 1
damage             魔像 受到 5 伤害（护盾吸收 0，生命 -5）→ 剩余生命 30
card_moved         斩击　结算区 → 弃牌堆
```

## 3.3 后续升级前必须知道的规则约束

这些是当前实现的既有约定，加 Buff / 多敌人时最容易踩：

1. **效果顺序是数据**：卡牌效果按 `ops` 数组顺序执行，且终局后立即停止后续效果。
2. **攻击牌计数**：先快照「此前已用攻击牌数」再自增，所以「追击」不会把自己算进去；技能不算攻击牌。
3. **护盾清除不对称**：玩家护盾在玩家回合开始清除，魔像护盾在敌方阶段开始清除。
4. **承伤回能的三个条件**：敌方行动、造成**生命**伤害、每次行动最多一次。被盾全吸不算，随从受伤不算。
5. **结算区**的存在是必需的：正在结算的过牌卡不会被本次洗牌抽回。
6. **意图数值锁定、目标实时**：`kind/value` 公开后不变，但目标每次读取时按嘲讽规则重算。

# 四、后续升级

> **2026-09-17 新设计方向（v0.2，未实现）**：融牌充能、1～10 点数，以及只比较上一张牌的同点／倍数／因数独立叠层；取消递增／递减特殊链。加入调度、控制、转换等特殊效果牌。规则与逐卡提案同步于 `设计元素表.xlsx`，详见 [融牌、点数与特殊效果牌：卡牌体系重构草案](plans/2026-09-17-fusion-points-design.md)。下列路线保留为此前方案；涉及免费普攻回能与流派核心的内容，需在新体系验证后重新评估。

> **卡池扩展 v0.3（评审提案，未实现）**：主要功能牌正常入牌组，少量场景／仆从生成临时牌；补充8种功能牌、6种场景和8种仆从的基础效果、获取与使用方式。见 [获取与使用、场景／仆从卡池](plans/2026-09-17-card-acquisition-scenes-minions-design.md)。费用与单位数值待验证，新牌的三类即时强化曲线尚未全部定稿。

> 方向：**让不同构筑对同一种敌人压力，产生不同的应对方式。**
> 已有基础（免费普攻回能、技能花能量、随从自动攻击）很适合往 **Buff 联动、多敌人目标选择、多流派资源循环** 扩展。

## 4.1 设计原则

1. 不要只做「伤害 +10%」这种普遍有效的提升，要让玩家**改变行为**。
2. 强力行为**提前显示**，玩家至少有一次应对机会。
3. 压力应该促使玩家**做选择**，而不是突然惩罚玩家。
4. 敌人数量增加时，**下调每只怪的伤害**，不能直接把单怪数值复制多份。
5. 百分比效果需要**统一取整规则**。

**最推荐的第一个切片：同一场双敌人战斗 + 三套可选牌组。**
这比立即堆大量关卡更容易验证：游戏的乐趣究竟来自战斗决策，还是仅仅来自数值变化。

## 4.2 分阶段路线图

| 阶段 | 加入内容 | 验收标准 | 对现有代码的影响 | 状态 |
|---|---|---|---|---|
| **第一步** | 两敌人战斗、随从集火标记、一张群攻牌 | ① 集火目标死亡后，后续随从攻击最左侧存活敌人<br>② 群攻牌对每个敌人分别结算护盾<br>③ 敌方总伤害不显著高于单敌人版本 | `BattleState` 从单敌人改为敌人列表；随从攻击需解析目标并处理目标中途死亡；新增群攻目标类型；UI 需多敌人布局与点选 | 待开始 |
| **第二步** | 力量、蓄势、虚弱、中毒 | ① 蓄势只被「造成伤害的技能」消费<br>② 虚弱按取整规则生效，界面显示取整后数值<br>③ 中毒在敌方阶段开始结算，不触发承伤/普攻回能<br>④ 力量只影响攻击牌类型 | 需要 Buff 容器与结算钩子（伤害计算前/后、回合开始/结束、敌方阶段开始）；新增 buff 相关事件类型供界面播放 | 待开始 |
| **第三步** | 连击、蓄能、防御三套预设牌组 | ① 三套牌组都能通关同一场战斗<br>② 切换牌组后初始牌组返回不同的 20 张 | `CardDB.initial_deck()` 目前固定返回同一副牌，需改为可切换；开局需要选牌组入口 | 待开始 |
| **第四步** | 随从强化、中毒专属卡 | ① 随从攻击力可被战旗加成<br>② 中毒层数可被催化提高 | 随从需要可被强化的字段；中毒需要独立的「失去生命」结算入口 | 待开始 |
| **第五步** | 战后选牌与多场连续战斗 | ① 连续两场战斗之间构筑保留<br>② `restart()` 仍能完全重置 | 当前 `restart()` 会重置全部状态，需引入跨战斗持久化与战后奖励流程 | 待开始 |

## 4.3 第一批 Buff

| 效果 | 建议规则 | 带来的决策 |
|---|---|---|
| **力量** | 本场战斗中，攻击牌伤害提高 X | 多次普攻更有价值，适合连击流 |
| **蓄势** | 下一张伤害技能额外造成 X 点伤害，触发后清除 | 先强化，再选择值得投入的大技能 |
| **虚弱** | 下一次攻击行动伤害降低 25%，之后移除 | 优先压制即将重击的怪物 |
| **中毒** | 敌方阶段开始时，损失等于层数的生命，随后层数减 1 | 挂毒后转向防守，等待持续伤害 |

第二批再做 **易伤**（下次受伤 +50%，触发后移除）与**反击**（本轮每受一次攻击反打，被盾挡住也触发）。

> 关键：有蓄势时值得保留大技能；敌人易伤时要注意出牌与随从攻击顺序；敌人中毒快死时可以把攻击转向其他目标；面对重击时虚弱可能比单纯增加护盾更有效。

## 4.4 怪物压力

| 类型 | 示例怪物 | 行为规则 | 玩家要解决的问题 |
|---|---|---|---|
| **即时压力** | 狂暴兽 | 本轮攻击 6，下轮重击 16 | 提前攒盾、保留虚弱，或集中输出抢先击杀 |
| **成长压力** | 战鼓祭司 | 每隔一轮为所有敌人 +1 力量 | 先解决眼前攻击者，还是先清掉强化队友的祭司？ |
| **数量压力** | 孵化者 | 每两轮召唤一只低血量小怪，敌方最多 3 个 | 检验群攻、集火与持续输出（**必须设数量上限**） |
| **资源压力** | 诅咒法师 | 每隔两轮向弃牌堆塞一张「废牌」 | 过牌与清理废牌产生价值（**建议后期再加**） |

## 4.5 多敌人与集火标记

规模：**先支持 2 个敌人，再扩展到最多 3 个。**

最有价值的变化是：**攻击谁，也变成一种防守选择。**

推荐组合（按优先级）：

1. **攻击者 + 强化者**（最推荐）—— 狼负责攻击，祭司负责强化。规则简单，却已经能让单体爆发、群攻、防守反击和中毒产生不同打法。
2. **守卫 + 脆弱输出者** —— 先打守卫，还是用技能绕过保护？
3. **两只交替重击的怪物** —— 如何安排每轮防御，优先击杀哪只？
4. **召唤者 + 小怪** —— 清场保安全，还是冒险集火召唤者？

**随从集火标记**（保留自动攻击的流畅性，同时给玩家目标选择权）：

- 玩家点击一个敌人，指定为随从集火目标
- 所有随从在回合结束时自动攻击该目标
- 目标死亡后，后续随从自动攻击**最左侧存活敌人**
- 改变标记**不消耗资源**

## 4.6 五套流派

| 流派 | 循环 | 优势 | 弱点 |
|---|---|---|---|
| **连击流** | 免费攻击 → 回能 → 累计攻击次数 → 技能收尾 | 节奏快，能量获得稳定 | 依赖攻击牌数量，手牌不足时输出下降 |
| **蓄能流** | 普攻、调息攒能量 → 获得蓄势 → 大技能爆发 | 集中击杀高威胁目标 | 准备阶段输出低，容易受成长型怪物压迫 |
| **壁垒反击流** | 叠护盾 → 抵挡敌人 → 反击或盾击 | 擅长应对多次小攻击 | 面对持续强化或非攻击型敌人时需主动解决威胁 |
| **中毒消耗流** | 给敌人挂毒 → 用虚弱和护盾减压 → 等毒伤击杀 | 适合多目标伤害分配，对护盾型敌人有优势 | 即时击杀能力弱，应对重击和召唤者时吃力 |
| **随从指挥流** | 用普攻攒能量 → 召唤随从 → 强化与保护 → 自动输出 | 随从存活越久收益越高 | 前期投入大，随从死亡会损失已投入资源 |

流派之间要能**混搭**：连击+蓄能、防御+中毒、防御+随从、蓄能+随从。这样一张奖励牌既可能强化原流派，也可能打开新方向。

关键卡与逐卡设计见 `docs/PVE卡牌Demo_升级方案.xlsx` 的「流派」表。

# 五、待决策问题

进入对应阶段前需要先关闭这些条目（详见升级方案 xlsx 的「待决策」表）：

| 编号 | 问题 | 建议 |
|---|---|---|
| **Q1** | 百分比效果（虚弱 25%、易伤 50%）的统一取整规则 | 统一为「向下取整，最低 1 点」，界面显示取整后结果 |
| **Q2** | 力量与蓄势如何叠加？是否设上限？ | 力量线性叠加、蓄势可叠加且一次性消费，两者都设上限 |
| **Q3** | 中毒的「失去生命」是否无视护盾？ | 建议无视护盾直接扣生命（与「失去生命」而非「受到伤害」的措辞一致） |
| **Q4** | 中毒在敌方阶段开始时结算，与敌人行动、终局判定的先后 | 先结算中毒并**立刻**做终局检查；若因此全灭则不再执行敌人行动 |
| **Q5** | 反击每回合最多触发几次？ | 按「受到攻击的次数」触发，不设额外上限，数值给低（2~3） |
| **Q6** | 集火标记在目标死亡后是清空还是顺延？ | 自动顺延到最左侧存活敌人，不清空标记 |
| **Q7** | 三套预设牌组各自的卡池边界？ | 每套约 20 张、只替换核心卡，公共卡（斩击/格挡）保留以保证可比性 |
| **Q8** | 敌人数量增加时，每只怪的伤害下调比例？ | 以「总压力大致不变」为原则先给一版，再由试玩调整 |

## 6.4 环境注意事项

- 请使用**标准（非 mono）构建**。mono 版在未安装 .NET 8 时会打印 `.NET: Failed to load compatible .NET runtime`；本项目只用 GDScript，不受影响，但建议直接用标准构建以免刷屏。
- `user://` 指向 `%APPDATA%\Godot\app_userdata\<项目名>`。该目录不可写时 Godot 会提示无法写日志与着色器缓存，不影响玩法。

# 数据库与实体关系设计

版本：v3.1｜日期：2026-10-30｜状态：新版数据目标；现有存档与Codec未修改。

## 1. 存储方案与边界

采用只读JSON内容和本地聚合JSON存档，不增加SQL或双写。ContentDB解释定义，领域服务解释规则，SnapshotCodec解释领域快照，SaveStore只负责文件外壳、完整性与IO。精确v1字段与方法保存在Git 历史，本文不将新字段假称已有实现。

| 数据 | 生命周期与位置 |
|---|---|
| 内容包 | 只读定义、manifest、ruleset；当前data仍为v1，新包独立版本化 |
| 当前局 | user://saves中的玩家存档，包含稳定战斗与完整四流随机快照 |
| Profile / Settings | 长期去重/解锁与用户设置分开保存，分别报告错误 |
| artifacts | 文档快照、测试证据、研究表格，不作为玩家存档来源 |

## 2. 内容关系

```text
CharacterDef → 专属CardDef集合 + 公共池资格 + 机制定义 + 被动/起手
CardDef → 基础/升级/考试有效面 → 受限EffectSpec
CardDef → UnitDef / SceneDef（仅有引用的牌）
EncounterDef → TaskDef阶段与意图
Manifest → 启用定义闭包 + ruleset + 内容版本/hash
```

每张永久牌只有一个人物归属或公共归属，主流派及支持分组是标签，不同人物路线数可不同。角色不再强制关联初始饰品。解题发表与旁听笔记是两种衍生CardDef，不进入永久/奖励。目标目录172永久+2衍生、3单位、2场景；六章基础/常驻共享原卡定义；精确schema和资源定义的物理组织须新版G0冻结。

## 3. 实例与聚合关系

| 聚合/实体 | 必须保留的语义 |
|---|---|
| RunState | 人物、精力、生活费、永久卡实例、地图、节点进度、已见事件、冻结奖励/库存 |
| PermanentCard | 唯一实例ID、定义ID、升级级别；同定义多张互不覆盖 |
| BattleCard | 独立战斗实例ID、可空永久来源、当前牌区与顺序、临时修正、实例限次 |
| BattleState | 主角资源、被动/能力计数、任务阶段/意图、单位、场景计次、DDL、牌区、来源顺序 |
| SessionState | 当前run/battle、唯一revision、终局摘要、Profile待提交标记 |
| RunSummary | run_id幂等键，终局后不改写同ID结果，不因重启再次奖励 |

论文状态须保存是否开题、本篇已用牌名集合、回合同名使用集合、进度/引用/修正/增幅和唯一R3-T201实例位置。前两集合生命周期不同：发表清本篇、不清本回合次数。旁听笔记统一牌名；章节复印保留源定义/牌名和临时不可部署覆盖，不能自动变成永久卡。

论文区保存三个有序槽、实例部署生效回合、自然/额外激活记录；换区/换序不刷新限次。任务实例保存六种负面及各自窗口/层数；阶段替换清旧状态。战斗另存每目标诱发本回合次数/首次、复合反应机会、检索连锁剩余抽牌、侵蚀合格施加批次及循证爆发限次；自然/提前侵蚀与诱发事件不可混淆。待选中的出牌快照留在内存续算队列，稳定档不保存半条效果。

林序保存前一出牌、策略/连携计数、被动机会、实例本战成功使用次数及有限准备；第二次增强不继续成长。伙伴保存当前/最大精力、协作/支援修正、入场顺序、正常及额外行动回合记录，短驻场不得按基础上限重建。能力保存来源/起效回合、场景保存升级/剩余2次及与能力共同创建顺序；临时保留保存到期窗口。

## 4. 稳定快照

稳定快照须覆盖继续游玩所需的领域数据、内容版本/hash、schema/算法版本、完整四流状态、冻结候选、终局摘要和提交标记。保存不重新抽取随机，不依赖字典遍历恢复来源顺序。seed及64位状态按明确版本化编码保存，不能因JSON精度丢失。

唯一pending_choice和续算队列是内存工作区，未完成不能保存为半条效果。进程中断恢复最近成功写盘的稳定状态。编码/解码在副本执行，发现不变量错误不得发布部分局。

## 5. 文件事务与备份

SaveStore读取/检查外壳、checksum及文件状态；写入先生成临时文件、校验后原子替换，按约定保留备份。不能由SaveStore补内容元数据、迁移卡牌或初始化损坏领域。

正式档和备份都不存在才允许首次初始化。正式缺失但备份存在/损坏，或正式损坏/不兼容，保留诊断，不当作空进度。继续只读正式档，备份恢复须明确选择。IO失败保留原件并可重试，不重新执行业务命令。

明确重开需要先验证新局，处理可解码终局的待提交摘要；旧档损坏或不兼容时，先原样归档正式与备份并校验SHA-256，再写入新局。任一步失败保留旧局，归档不能伪造通关摘要。

## 6. 跨文件终局提交

1. 稳定写当前局：保存不可变terminal_summary与profile_merge_pending=true。
2. 按run_id幂等合并Profile；重复提交不重复奖励或解锁。
3. 再写当前局，仅清待提交标记，保留摘要与事件日志。

三个步骤分别报告成功/失败。重启或显式保存可重试未完成步骤，不能回滚成未结算战斗再发一次奖励。自动保存关闭时仍须遵守明确替换旧局的写盘约束。

## 7. 版本兼容策略

旧卡概念索引不是可执行迁移表。相同人物ID不能解释不同版本被动；新R3卡不能覆盖旧定义。未来必须选择并验证并行读取v1，或拒绝不兼容并允许原样归档后重开。未独立验证前禁止自动迁移玩家档。

新版schema、字段名、checksum范围与升级路径待新版G0冻结；旧g0.json与既有证据hash不修改。后续验证须包含论文两集合/唯一发表、章节顺序及激活、六负面/窗口、诱发次数及施毒计数、伙伴实例上限及额外行动、能力/场景时序、实例限次、冻结候选恢复和每个终局提交故障点。本轮没有执行这些游戏测试。

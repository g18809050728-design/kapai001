# 数据库与实体关系设计

版本：v0.2｜日期：2026-10-15｜状态：G5 聚合快照、领域 Codec、文件存储与幂等合并已实现；正式验收状态见根计划

关联文档：[初步架构设计 §10](初步架构设计.md)、[接口文档](接口文档.md)、[内容层契约 §7](内容层契约.md)

## 1. 数据库方案

本版采用**只读JSON内容库＋内存ID索引＋本地JSON聚合快照**。ContentDB是内容访问组件，不是SQL数据库连接。以下“实体、主键、引用”定义同样适用于JSON，约束由加载器与快照校验器执行。

| 方案 | 优点 | 成本/适用情况 |
|---|---|---|
| JSON与内存索引（选用） | Godot直接读写，内容易审查，完整局状态一次保存 | 需显式实现引用校验、备份和跨文件恢复 |
| SQLite | 唯一键/事务/历史查询方便 | 通常需要Godot扩展；战斗仍需对象重建，不改善当前核心规则问题 |
| 服务端数据库 | 支持账号、联网和多设备 | 当前离线玩法没有对应需求 |

选择依据：内容规模约百级、一个进行中局、主要读写整局快照，无大量跨局聚合查询。若历史统计需要分页、多条件检索或规模经测量不适合文件，再将Profile历史摘要迁移SQLite，保持规则层接口不变。首版不同时维护JSON和SQL两套权威状态。

## 2. 三类数据与物理位置

| 数据域 | 物理位置 | 生命周期/权威来源 |
|---|---|---|
| 内容定义 | `res://data/definitions/*.json` | 发布版本内只读；精确 JSON 键见内容契约 §8，G2 已创建并整包验证 |
| 内容清单 | `res://data/manifests/campus_mvp.json` 与独立测试 fixture | 启用ID、显式覆盖及规则集ID；G2 已核对全部 66 个冻结 ID，holdback=0；不预设 `full` 存在 |
| 当前局 | `user://saves/current_run.json` | 一整个SessionState稳定快照 |
| 长期进度 | `user://saves/profile.json` | 解锁、图鉴、教学和去重局摘要 |
| 设置 | `user://saves/settings.json` | MVP仅autosave；后续音量、显示、输入字段先扩充接口，与存档进度独立 |

每个可写文件旁保留`.bak`和写入中的`.tmp`。目录与槽位由SaveStore固定映射，UI只传槽位，不传任意文件路径。

## 3. 标识与通用约束

- 定义键是`(kind, id)`；P/K/F等现有ID沿用策划。不同内容版本下相同ID可以改变数值，因此恢复必须校验content_version/hash。
- 运行实例ID为`run_id + 单调序号`生成的不透明字符串，不使用对象地址。next_instance_seq随快照保存；ID生成不消费战斗随机。
- run_id新局生成一次；新局revision从0开始，继续游戏恢复快照中的revision。若首次保存失败，run_id仍属于当前内存局，但不声称已落盘；永久卡进入战斗时生成新battle_card_id，用origin_card_id关联，不覆盖永久实例ID。
- 升级级别0或1，钱≥0，永久牌组下限5；各上限从rulesets.json取值。
- 存活对象引用必须存在且属于同局/同战斗；历史来源使用值描述，不要求来源对象仍存活。
- JSON数组负责顺序、对象键负责索引；牌堆顺序不能由字典遍历推断。所有副本必须深拷贝可变子集合。

## 4. 内容实体与关系

下表PK表示主键，FK表示加载时校验的引用；附属结构不强制拆独立文件。

本表只索引实体关系，不另定义JSON schema；下列字段名与[内容契约 §8](内容层契约.md)一致，完整必填/可选字段及校验只在那里维护。G2 已实现 ContentDB 运行 schema 与引用闭包校验；内容能加载与具体玩法行为验收分开记录。

| 实体/建议文件 | PK与主要字段 | 关系与约束 |
|---|---|---|
| CharacterDef / characters.json | id、name_key、passive、starter_cards、starter_relic_id、art_key | starter_cards关联CardDef，额外数量2；饰品关联RelicDef |
| CardDef / cards.json | id、type、rarity、tags、cost、target、effects、upgrade、exhaust、art_key | effects引用单位/场景/状态/衍生牌时须存在；basic/special不是品质 |
| UnitDef / units.json | id、vitality、cooperation、support、guard、art_key | 支援行为引用已注册EffectSpec与StatusDef |
| SceneDef / scenes.json | id、modifiers、prepare_effects、prepare_random、battle_limit、art_key | 限次计数按场景定义保存，替换不重置 |
| RelicDef / relics.json | id、availability、rarity可空、hooks、effects、modifiers | starter获取限制允许rarity=null，不能进随机品质池 |
| StatusDef / statuses.json | id、stack_policy、duration_policy、dispel_policy、numeric_rule_key可空 | 已在rulesets中定义的cap/系数仅引用numeric_rule_key，禁止重复填数 |
| TaskDef / tasks.json | id、kind、phases[]、art_key | phases至少一个，含有序意图；阶段键在任务内唯一；考试限制仅在EncounterDef维护 |
| TaskPhaseDef / TaskDef内嵌 | `(task_id, phase_key)`、work_max、intents | 后继由阶段数组顺序决定，不允许循环回旧阶段 |
| EncounterDef / encounters.json | id、members[]、base_ddl、terms、exam_flags、scaling | 每个member引用TaskDef；允许重复定义如两个同种任务，但实例不同 |
| EventDef / events.json | id、terms、once_per_run、options[] | 选项ID在事件内唯一，条件/支付/收益分字段 |
| RulesetDef / rulesets.json | id、schema_version、run/battle/statuses等 | 数值权威来源，当前campus_v1 |
| ContentManifest / manifests目录 | id、ruleset_id、enabled、overrides | 启用内容的引用闭包必须完整；覆盖可追踪 |

EffectSpec 为有限注册的值结构。当前内容示例以 `{op, ...该 op 的字段}` 表示（如 `{op: complete, amount: 14}`），不要求新增 `params` 包装层；精确键名与逐 op 约束见内容契约 §8，G2 已实现并验证 schema。目标和条件不接受可执行脚本；定义层不复制运行状态。

内容关系（基数）：

```text
CharacterDef 1 ── N StarterCardEntry N ── 1 CardDef
CharacterDef N ── 1 RelicDef（初始饰品）
CardDef 1 ── N EffectSpec ── 0..N 其他定义引用
EncounterDef 1 ── N EncounterMember N ── 1 TaskDef
TaskDef 1 ── N TaskPhaseDef 1 ── N IntentSpec
ContentManifest N ── 1 RulesetDef
ContentManifest N ── M 内容定义（启用集合）
```

## 5. 局内实体

| 实体 | PK/字段 | 所属与约束 |
|---|---|---|
| SessionState | revision、run、battle可空、random_snapshot、terminal_summary可空、profile_merge_pending:bool、event_log | 唯一revision、随机快照和终局摘要持有者；清理仅清 bool、摘要与日志继续保留；run_id由run派生，整个current_run文件保存 |
| RunState | run_id、character_id、ruleset_id、difficulty、manifest_id、term、money、vitality、max_vitality、next_instance_seq | character/ruleset关联定义；战斗中vitality只是入场值 |
| RunCard | card_id、definition_id、upgrade_level、acquired_from | N:1 RunState；N:1 CardDef |
| OwnedRelic | relic_id、definition_id、slot、acquired_order | N:1 RunState；同局definition_id唯一、slot唯一，0≤slot<6 |
| NodeState | node_id、term、layer、kind、status、next_ids、context | N:1 RunState；连线目标存在且只能前进 |
| CareerProgress | track、value | RunState内字典，四轨各0～3，不独立发ID |
| RewardOffer | offer_id、source_node_id、items[] | N:1节点；完成后可留领取标记 |
| RewardItem | `(offer_id,item_id)`、kind、candidates、status、chosen_id可空 | 候选生成后冻结；status为pending/claimed/skipped |
| ShopState | shop_id、node_id、stocks[]、removal_count | 节点内0或1；每节点删除次数校验 |
| StockItem | `(shop_id,stock_id)`、kind、definition_id可空、price、sold | 餐食无需定义ID；同类不重复定义，售出不补 |
| EventState | event_instance_id、node_id、definition_id、resolved_option_id、frozen_candidates | 节点内0或1；离开也记录已见 |
| TermSettlement | settlement_id、term、steps[] | 子步骤有完成标记，恢复和履历不能重复发 |
| RunSummary | run_id、result、reason、ending_id可空、统计与解锁候选 | 与run_id一一对应，finalize 后不可改写同ID结果；完整 B08 选去向前仅有 ending_draft，不生成 RunSummary |

节点context为受kind约束的联合类型：battle引用encounter_id；shop含ShopState；event含EventState；rest含已用动作。不能同时挂商店与事件数据。

永久牌删除后其ID不会复用；战斗中不能删永久牌。因此存活BattleCard的origin引用不会在本战突然失效。删除和替换属于当前局动作，不删除任何内容定义。

## 6. 战斗实体

| 实体 | PK/主要字段 | 关系与约束 |
|---|---|---|
| BattleState | battle_id、node_id、encounter_id、character_id、difficulty、exam_flags、phase、round_index、ddl、player、card_by_id、zones、units、tasks、statuses、scene、counters、resolution、next_instance_seq、next_creation_order、source_registry | 当前SessionState至多一个活动战斗；round从1开始；next_instance_seq生成实例ID，next_creation_order排序触发来源 |
| PlayerBattleState | entity_id、vitality、max_vitality、relax、focus | 每战恰好一个；不复制钱包和永久牌组 |
| BattleCard | card_id、definition_id、origin_card_id可空、upgrade_level、modifiers、retained_until_discard | N:1 BattleState；origin非空指向本局RunCard |
| CardZones | draw/hand/discard/exhaust/resolving的有序ID数组 | 每张BattleCard在且只在一个数组；数组元素不得重复 |
| UnitState | unit_id、definition_id、vitality、max_vitality、relax、cooperation、entered_order、last_acted_round、actions_taken、target_id可空 | definition_id→UnitDef；最多3个存活单位；目标失效允许清空并选回退目标 |
| TaskState | task_id、definition_id、phase_key、work_remaining、work_max、shield、intent_cursor、intent_snapshot、entered_order、eligible_round | `(definition_id,phase_key)`→TaskPhaseDef |
| StatusState | status_id、definition_id、holder_id、source、stacks、expiry、creation_order | holder必须属于本战；来源记录为值而非强FK |
| SceneState | scene_id、definition_id、established_round、pending_random_result | 每战0或1；场景消失不删除战斗级限次 |
| TriggerCounter | scope、owner_key、trigger_key、count、round可空 | 组合键唯一；回合计数到期重置，战斗计数保留 |
| ResolutionState | action、effect_cursor、queue、locked_target_ids、choice | 仅内存暂态，稳定存档中必须为null |

BattleCard不另存zone字段，以CardZones为唯一牌区权威，避免出现“卡记录在手牌但数组在弃牌”的双写矛盾。永久实例与战斗实例的关系是RunCard 1→N BattleCard（跨多场）；单场每个非空origin最多对应一张原始牌，未来复制牌必须为临时实例且用source描述来源。

触发来源引用已退出单位/旧首领时属于历史信息；待执行目标则必须在每段结算前重检。阶段转换创建新task_id，旧多段目标不会自动指向新阶段。BattleCodec同时保存next_creation_order与source_registry（来源ID、创建序、显示信息），恢复不重新编号；实体创建序与同窗排序遵循规则书[RES-001]。

### 运行实体关系总览

```text
Profile 1 ── N RunSummary（run_id唯一）
SessionState 1 ── 1 RunState
SessionState 1 ── 0..1 BattleState
RunState 1 ── N RunCard N ── 1 CardDef
RunState 1 ── N OwnedRelic N ── 1 RelicDef
RunState 1 ── N NodeState
NodeState 1 ── 0..N RewardOffer 1 ── N RewardItem
NodeState 1 ── 0..1 ShopState 1 ── N StockItem
NodeState 1 ── 0..1 EventState N ── 1 EventDef
BattleState 1 ── N BattleCard N ── 0..1 RunCard（origin）
BattleState 1 ── 1 PlayerBattleState
BattleState 1 ── 0..3 UnitState N ── 1 UnitDef
BattleState 1 ── N TaskState N ── 1 TaskPhaseDef
BattleState 1 ── 0..1 SceneState N ── 1 SceneDef
BattleState 1 ── N StatusState N ── 1 StatusDef
```

这是逻辑实体关系，不要求为每条关系落一张SQL表。JSON用聚合嵌套表达所有权，ID表达跨聚合/定义引用。

## 7. 快照布局与索引

当前局外层字段沿用接口文档，增加content_hash以区分同名但不同内容包：

```text
SaveSnapshot
  schema_version / content_version / content_hash / manifest_id
  run_id / revision / checksum
  random_state: 算法版本、map/reward/event/battle流seed和state
  payload:
    run: RunState（含next_instance_seq、已结算battle_id集合）
    battle: BattleState或null
    terminal_summary: RunSummary或null
    profile_merge_pending: bool
    event_log: 有界 LoggedRuleEvent 数组
```

外层revision、run_id、random_state各存一次；decode时重建SessionState。BattleStep.rng_state与RunStep.rng_states只是一次执行的输出快照，由GameSession合并，不在RunState/BattleState再保存第二份随机状态。

Profile快照payload：unlocked_ids、seen_content_ids、tutorial_flags、summaries_by_run_id、completed_runs；completed_runs 必须等于去重摘要数。Settings payload 为 `{autosave: bool}`，独立保存，ProfileView 在应用层合并显示设置。非局文档沿用同一外壳，用 manifest_id=profile/settings 标识文档类型，content_version/content_hash 默认空字符串，run_id/revision/random_state 为 null，不新增 kind 字段。

内存索引：定义按`kind→id`；运行实例按ID字典；牌堆为ID数组；节点按ID查询；摘要按run_id去重。品质/学期过滤可直接扫描小型定义集合，无需额外缓存。启动每次重建这些派生索引，不把索引复制进存档。

规范化编码：对象键按字符串排序，数组保持游戏顺序，仅用JSON基础类型；整数值 float 先规范化为 int，仅允许绝对值不大于 2^53−1 的数值整数，拒绝 NaN/Infinity 和非 JSON 值。64位seed/state编码为十进制字符串，避免 JSON 数字精度损失。checksum对排除checksum字段后的规范化UTF-8内容计算SHA-256；用于损坏检测，不是防作弊机制。

## 8. 提交、事务与跨文件一致性

### 一次游戏操作

每条命令以当前已发布状态（稳定状态或待选工作区）和随机状态的副本为起点：全部校验→执行至规则稳定边界或下一待选→校验不变量→一次发布本条命令的状态与随机变化；拒绝或异常时丢弃本条副本，已发布状态、revision及随机快照不变。待选工作区可以逐条确认并发布给当前进程，但不能执行其他规则命令，也不构成可持久化快照；只有效果队列完成后才成为规则稳定状态。`autosave=true` 时稳定提交后尝试写盘；关闭时仅显式保存或 save-and-exit 写盘。保存失败不回滚已发布的规则状态，只报告 `persistence=failed` 并允许重试保存；进程恢复从最近成功写入的稳定快照开始。JSON文件不能提供SQL事务，持久化原子性由聚合整体编码、临时文件校验和替换保证。

### 结局写入Profile

当前局与Profile是两个文件，不能声称一次重命名就能同时提交。只有包含待合并摘要的 current_run 已成功写盘后才开始合并 Profile；autosave 关闭时，合并由显式保存触发。采用可恢复的三步：

1. current_run写入终局结果、terminal_summary 与 profile_merge_pending=true，并成功保存。
2. 按run_id将摘要及解锁集合幂等合并进Profile，保存成功。
3. 只清除 current_run.profile_merge_pending 并保存，terminal_summary 保留；完成前不覆盖此局创建新局。

步骤2失败时保留已持久化的 pending；步骤3失败时重试合并因run_id已存在而不重复记录。加载正式档或备份后均先检查已持久化的待合并摘要；正式档继续会自动重试全部余下步骤，备份恢复允许合并 Profile 但暂缓第3步，返回 merged/pending 并保留正式 current_run 原文件，后续稳定保存才替换。解锁使用集合并集，completed_runs 从全部去重摘要计算（含胜利、失败和放弃），不重复加计数。Profile写入成功之前不展示“已永久解锁”。若首步写盘失败，摘要只在会话内待重试，不能报告已跨文件提交。第2步失败时报告`profile_merge=failed`、`profile_cleanup=pending`；第3步失败时报告`profile_merge=merged`、`profile_cleanup=failed`，分别携带错误；`save_and_exit()`在任一步失败时不释放会话。载入成功与重试部分成功分开，详情见 SessionView.profile_commit_status。若第3步失败后重启，读取pending并再次幂等合并，不得把已合并摘要计为第二份记录。

### 存档故障

同目录临时写入并读回校验→保留旧有效档→替换正式档。磁盘满、权限不足或程序中断时不删除唯一有效副本。保存失败只重试持久化，不再次运行购买、恢复或领奖。

## 9. 校验与迁移

加载分三层：结构和基本类型→主键/引用及内容兼容→领域不变量。任何层失败均返回明确错误，保留原档；不自动删未知卡或修复成“看似能运行”的局。

必查：重复实例ID；缺失定义；牌区遗漏/重复；超过槽位；同名饰品重复；负钱/负资源；升级超限；意图游标越界；非法节点边；已领取项无对应标记；resolution非空却被标为稳定；随机流缺失；终局待合并摘要run_id不匹配。

schema_version只表示快照结构；content_version/hash表示规则及定义；随机算法版本独立。SnapshotCodec.migrate 只在副本上执行调用方显式提供的迁移链，拒绝缺路径、循环及无效返回并重算 checksum，不执行磁盘写入。当前 GameSession 的 continue/restore 不隐式调用迁移，不兼容版本直接返回 VERSION_MISMATCH。未来启用旧档迁移时，调用方还须完成内容兼容与领域 decode 校验，再显式保存并保留原有效备份；不能将迁移函数返回成功视为旧档玩法兼容。

## 10. 验收案例

1. 同一K01的四个永久实例拥有不同ID，升级一张不影响另外三张。
2. 永久卡耗尽后下场重新出现，临时牌不进入永久牌组。
3. 首领新阶段task_id改变，旧锁定目标不可误指向新阶段。
4. 回合计数与战斗计数读档不刷新，L02预抽结果不重抽。
5. 购买饰品取消不改钱包、库存和装备；重复领奖被领取标记拒绝。
6. 在结局三步提交每个步骤中断，恢复后仅有一份摘要且解锁不丢失。
7. 原始存档和备份均损坏时提示错误，不能自动覆盖证据开新局。


## 11. 存储模块契约（src/storage/** 实现补充）

> 已实现模块：`src/storage/snapshot_codec.gd` / `save_store.gd` / `profile_merge.gd`，以及 `src/run/run_codec.gd`、`src/battle/battle_codec.gd`。测试入口为 `tests/run_tests.gd`，接入 `test_save_codec.gd`、`test_save_store.gd`、`test_snapshot_codec.gd`、`test_session_storage.gd`。
> 本节定义局流程会话接入存档时的唯一契约说明；工程存在不替代根计划要求的正式验收证据。

### 11.1 SnapshotCodec（全静态，不碰磁盘）

| 方法 | 签名 | 说明 |
|---|---|---|
| canonical_json | `(value) -> String` | 对象键排序的紧凑 JSON；整数值浮点先规范化回 int，保证「解析后再算 checksum」仍一致 |
| normalize_numbers | `(value) -> Variant` | 递归把 JSON 解析出的有限整数值 float 还原为 int（绝对值≤2^53−1） |
| compute_checksum | `(snapshot: Dictionary) -> String` | 对排除 `checksum` 后的规范化 UTF-8 内容算 SHA-256 |
| checksum_matches | `(snapshot) -> bool` | 校验和比对 |
| wrap_snapshot | `(payload, meta) -> Dictionary` | 通用外层组装（含 checksum）；名字避开内置 `wrap(value,min,max)` |
| encode_session | `(session, content_info) -> Result<SaveSnapshot>` | 协调 RunCodec / BattleCodec 并封装当前局；terminal_summary、profile_merge_pending、event_log 只从 SessionState 读取；**`battle.resolution != null` 时返回 `CHOICE_PENDING`** |
| encode_document | `(kind, payload, meta={}) -> Result<SaveSnapshot>` | 封装 Profile / Settings 等非局文档；`kind` 必须是已支持的文档类型 |
| validate_structure | `(snapshot) -> PackedStringArray` | 第 1 层：外层字段与基本类型 |
| decode_document | `(snapshot, expected_kind) -> Result<{payload, meta}>` | 结构、checksum、schema 和文档类型校验后返回副本 |
| decode_session | `(snapshot, content_db) -> Result<SessionState>` | 协调领域 Codec 重建 `SessionState`（包括持久摘要、待合并 bool 与日志），并完成兼容与领域校验 |
| migrate | `(snapshot, migrations={}) -> Result<SaveSnapshot>` | 副本上迁移；未提供路径返回 `VERSION_MISMATCH`（不假设兼容） |

`RunCodec` 独占 RunState 及其子实体的显式字段映射；`BattleCodec` 独占 BattleState 及其子实体的显式字段映射。SnapshotCodec 只封装/校验快照外壳并协调这两个领域 Codec，不重复映射领域字段。禁止按任意 `script_path` 实例化对象或自动序列化脚本变量。

`migrations` 形如 `{from_version: Callable(snapshot) -> snapshot}`；迁移成功会重算 checksum。它不写盘，也不替代 decode_session/decode_document 的目标类型校验。

### 11.2 SaveStore（文件存储）

```gdscript
var store := SaveStore.new("user://saves")   # 只做文件 IO / checksum，不注入内容库
store.inspect(slot)            -> Result<SaveMetadata>   # 不存在 = SAVE_NOT_FOUND；损坏时 valid=false 并带 problems
store.inspect_backup(slot)     -> Result<SaveMetadata>   # 同样只读，不自动恢复
store.save(slot, snapshot)     -> Result<SaveReceipt>
store.load(slot)               -> Result<SaveSnapshot>   # 文件结构与 checksum；兼容/迁移交给 SnapshotCodec
store.load_backup(slot)        -> Result<SaveSnapshot>
store.debug_hooks              # 仅测试：{"*" 或 slot: {"fail_write"|"truncate_temp"|"fail_after_backup"|"fail_rename": true}}
```

- 槽位：`current_run` / `profile` / `settings`（`GameConstants.SAVE_*`）。
- 文件：`<base>/<slot>.json`（正式）、`.json.bak`（上一份有效档）、`.json.tmp`（临时）。
- **保存顺序**：校验外壳/checksum → 写临时 → 读回校验 → 旧有效档转备份 → 替换正式档。任一步失败返回 `SAVE_IO_ERROR` / 具体校验错误，**保留至少一份有效旧档**。
- 旧正式档损坏时不覆盖既有备份；替换阶段失败会从备份还原正式档。
- `save` 不更改调用方快照、不补元数据、不解释玩法；GameSession 先经 SnapshotCodec 使用 ContentDB 校验兼容和领域不变量，再传有效快照。

`SaveReceipt = {slot, saved_at, revision, checksum}`；实际 DTO 保留 G1 的 written_at，saved_at 为同一值的读写属性别名，不在快照外壳额外保存时间戳。非局文档 receipt.revision=0；
`SaveMetadata = {slot, path, saved_at, schema_version, content_version, revision, checksum, valid, problems}`。

### 11.3 快照字段表

| 字段 | 类型 | 说明 |
|---|---|---|
| schema_version | int | 已实现 `SNAPSHOT_SCHEMA_VERSION = 1` |
| content_version / content_hash / manifest_id | String | 当前局做内容包兼容；GameSession 传 ContentInfo，SnapshotCodec 封装；非局文档类型规则见 §7；SaveStore 不补齐 |
| run_id | String 或 null | 当前局必填；Profile/Settings 为 null |
| revision | int 或 null | 当前局写操作版本；Profile/Settings 为 null |
| random_state | Dictionary 或 null | `RandomSource.export_state()`，seed/state 为十进制字符串 |
| payload | Dictionary | 当前局：`{run, battle, terminal_summary, profile_merge_pending, event_log}`；Profile/Settings：文档本体 |
| checksum | String(64) | 排除自身后的 SHA-256 |

`payload.run` 为 RunState；`payload.battle` 为 BattleState 或 null（稳定边界 `resolution` 必为 null）；`payload.terminal_summary` 为 RunSummary 或 null（其 `run_id` 必须等于当前局 `run_id`）。profile_merge_pending=true 必须有 finalized 摘要；清理后 bool=false，摘要仍在。awaiting_ending 时摘要为空、bool=false；日志上限及消费键见接口 §8。

### 11.4 三层校验

1. 结构 + checksum + schema → `SAVE_CORRUPT` / `VERSION_MISMATCH`。
2. 内容引用与兼容（需 catalog）：未启用定义 → `CONTENT_INVALID`；content_hash / manifest_id / ruleset_id 不一致 → `VERSION_MISMATCH`。
3. 领域不变量 → `SAVE_CORRUPT`：`SessionState.validate()`、`RunState.validate(relic_slots)`、`BattleState.validate(unit_slots)`、稳定边界无 resolution、待合并摘要 run_id 匹配、已结算战斗不得仍挂在场。

### 11.5 结局三步提交

`GameSession._commit_pending_profile(defer_cleanup: bool = false)`返回`Result<ProfileCommitStatus>`；`ProfileCommitStatus = {profile_merge, profile_cleanup, profile_error, cleanup_error}`。无待合并摘要时返回`not_pending / not_needed`；部分成功仍通过`Result.ok=true`及状态字段报告。第二步失败保留`profile_merge=failed / profile_cleanup=pending`，第三步失败保留`profile_merge=merged / profile_cleanup=failed`；不得把Profile已写入误报为合并失败。defer_cleanup=true 用于备份恢复，合并后暂缓清理并返回 merged/pending。第三步只在current_run写入成功后才清除内存中的待合并标记；失败时保留标记供重试。会话层按[接口文档](接口文档.md)形成`SessionSaveResult`，并将状态副本放入 SessionView.profile_commit_status。

1. 在 current_run 已写盘前提下检查 payload.profile_merge_pending；false 返回 not_pending。true 时读取已 finalized 的 payload.terminal_summary；为空或 run_id 不符则 SAVE_CORRUPT。
2. `ProfileMerge.merge(profile, summary)` 后保存 `profile`：同一 `run_id` 只记一份摘要，`completed_runs = summaries_by_run_id.size()`，`unlocked_ids` / `seen_content_ids` 取并集并排序。
3. 在副本上只置 profile_merge_pending=false，保存成功才同步内存 bool；摘要与日志保留。

第 2 步失败保留 pending；第 3 步失败后重试因 `run_id` 已存在而不重复记录；Profile 损坏时返回其错误，不静默覆盖。

`ProfileMerge.default_profile()` 返回全部五字段的空值；`validate(profile)` 严格校验字段、类型、唯一 ID、摘要键/run_id 对应及 completed_runs；`merge(profile, summary)` 返回新副本。相同 run_id 的相同摘要幂等；同 run_id 不同 finalized 摘要返回 SAVE_CORRUPT，原 Profile 不变。unlocked_ids / seen_content_ids 取去重排序并集，tutorial_flags 保留原值。

### 11.6 跨模块验收边界

BattleState.validate 已将玩家、存活单位与有效任务列为合法状态持有者；未知持有者拒绝加载，且状态定义须允许该类目标。SnapshotCodec 协调并报告领域校验结果，战斗聚合负责定义并验证合法引用集合。任务离场/阶段转换后的引用清理属于引擎行为，不能靠读档时删掉非法状态来掩盖。

### 11.7 摘要与职责边界

RunService 负责终点 finalize，GameSession 持有 terminal_summary 和提交 marker；ProfileMerge 是纯函数，只合并 finalized 摘要与集合。SaveStore 仅文件完整性；SnapshotCodec 负责结构版本、内容兼容及迁移协调，领域 Codec 独占字段映射。备份恢复由 GameSession 显式触发，只有无内存局时发布，载入时不覆盖正式档。稳定存档禁止 resolution 非空，不能把内存待选游标的编解码当作稳定档支持。

continue_run 只读正式 current_run，不静默回退；start_run 在正式损坏/不兼容、活动局或 pending 摘要时拒绝覆盖，正式缺失但备份存在/损坏时也保留证据。Profile/Settings 仅在各自正式与备份都不存在时使用默认值；正式缺失但备份存在/损坏时返回错误，不能作为首次启动初始化覆盖。ProfileView.error/settings_error 分别公开这两类诊断；当前公开恢复入口仅恢复 current_run 备份，不假装已提供 Profile/Settings 恢复 UI。

MVP 不启用履历、传承或毕业解锁；仍使用同一三步结构记录胜利/失败/放弃摘要，解锁候选为空。长期计数从去重摘要派生，UI 只展示 Profile 真正写入成功的记录。
